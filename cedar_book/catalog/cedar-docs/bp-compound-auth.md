# 复合授权

复合授权指一次用户活动需要多次独立授权查询才能判定是否允许。原文的例子很直观：在文件系统里移动一个文件，可能要同时具备三项权限——从源目录删除文件、向目标目录添加文件，以及（视应用而定）修改文件本身。这不是设计缺陷，而是常态。

## 为什么不要强求单次查询

刚接触授权建模的人容易假设“每个授权决策都必须由一次查询解决”。原文指出，这个假设会逼出过度复杂的模型和绕来绕去的策略语句。把操作拆成足够小的原子动作后，移动文件这类复合操作自然表现为几个原语的聚合，这反而是模型设计良好的标志。判断标准可以概括为：原子动作是否各自可理解、可复用，复合操作是否能由它们直观拼出。

## 多方同意形成的握手

另一种复合场景出现在“授权需要多方共同决定”时。以组织目录为例，用户可以隶属多个组。最简单的做法是让组所有者有权添加任何人；但如果要求被添加者本人先同意，就形成了双向握手：调用方必须同时确认“操作者有权限把成员加入该组”和“被添加的用户同意被加入该组”。

实现上可以给用户增加一条权限，规定其能否被加入任意组或某个特定组。当调用方尝试添加成员时，应用要同时校验这两侧。原文提醒，存在 N 方握手时，通常会看到 N 次复合授权查询，每一方各查一次。

## 识别信号

当设计难题涉及多个资源、又说不清权限该如何建模时，往往就是复合授权的信号。此时不要硬凑一条覆盖全部资源的策略，而应把操作分解成多个独立的授权检查。批量操作也是同一思路：对批次中的每个资源各做一次单资源判断，再按结果过滤，具体模式见[授权模式](./auth-patterns.md)中的“批量读、改、删”。

## 与细粒度权限的关系

复合授权能成立的前提是动作已经拆细。如果只有笼统的 `Write`，移动文件就无法区分“从源删除”和“向目标添加”，只能写一条过宽的允许。因此[细粒度权限](./bp-fine-grained-permissions.md)是复合授权的基础：先在模型里保留最小动作，再在调用侧组合。分解后的每个原子判断也更容易交给[元权限](./bp-meta-permissions.md)或审计逻辑分别处理。

原文最后强调，复合授权不是需要消除的例外，而是应当预期的正常形态。把“一次操作 = 多次查询”当作默认假设，策略会更短，应用代码里的判断顺序也更清晰。
