# 最佳实践概览

这是 Cedar 官方最佳实践的入口页，内容是一份持续更新的建议清单，目标是让 Cedar 作为授权引擎发挥最大价值。原文只有一段导语和 17 条链接，没有展开论证；下面按主题重新组织，便于按建模顺序阅读。

## 清单的结构

原文的 17 条建议依次是：

- 定义并使用命名规范
- 识别你的授权模式
- 把动作映射到业务领域
- 在 Cedar 中建模所有权限
- 填充策略作用域
- 利用用户组
- 复合授权是常态
- 模型中用细粒度权限，界面上聚合权限
- 用属性或模板表达关系
- 每个资源都生活在容器里
- 把主体与资源容器分开
- 调用授权 API 前规范化输入数据
- 不要用 context 存放主体、动作、资源的信息
- 把元权限实现为策略
- 避免策略中的可变标识符
- 把 RBAC 作为授权策略的一部分
- 考虑其他需要查询授权的理由

这些条目不是彼此独立的技巧，而是一条从命名、建模到请求构造的流水线。下面按四组说明它们各自解决什么问题。

## 命名、动作与授权模式

前三条规定了“怎么称呼”和“怎么切分”。命名规范让实体类型、动作名和属性名在 schema、策略与代码中保持一致，减少拼写类和映射类错误。动作要映射到业务领域，即一个动作对应业务上真实发生的一件事，而不是数据库的 CRUD 原语；这样策略才读得懂，也更容易复用。识别授权模式则是为每个 API 端点确定它属于单资源读写、资源创建、列表、批量、开放端点还是隐式作用域，从而决定请求里的主体、动作、资源和实体切片。六种模式的完整拆解见[授权模式](./auth-patterns.md)。

## 权限建模

“在 Cedar 中建模所有权限”强调不要留一半逻辑在应用代码里：只要涉及“谁能做什么”，就应写进策略，否则审计和变更都会出现盲区。填充策略作用域指的是尽量把 `principal`、`action`、`resource` 写具体，而不是一律留空后靠 `when` 兜底，具体作用域能让策略更易读、验证更有力，写法可参考[策略示例](./policy-examples.md)。

用户组和 RBAC 解决规模化问题：把权限授予角色或组，再让用户成为组成员，比给每个人单独写策略稳定得多。复合授权是常态，因为一次业务操作往往对应多个资源的多次判断，不能假设一次 `IsAuthorized` 就能覆盖整个请求。细粒度与聚合的分工则是：模型中保留最小粒度的权限，界面再把它们打包成用户看得懂的选项。

## 资源、关系与上下文

“每个资源都生活在容器里”和“把主体与资源容器分开”是层级建模的两条骨架规则：资源通过 `in` 挂在租户、账户、文件夹、相册等容器下，主体则不要塞进资源容器层级，否则权限会沿错误的路径继承。关系可以用属性表达，也可以用模板表达，选择取决于关系是否稳定、是否需要频繁变更；实体与层级的基础见[实体与实体层级](./entities.md)，模板见[策略模板](./templates.md)。

Context 只放随请求变化的信息，例如 IP、时间、MFA 状态；主体、动作、资源本身的属性应放在实体上，否则同一事实会有两个来源，策略难以验证。输入数据要在调用授权 API 前规范化，避免大小写、空白或编码差异让匹配失效——这也是[安全模型](./security.md)中的一条硬要求。

## 标识、元权限与其他查询

元权限指“谁可以管理权限”这类权限，例如谁可以修改某相册的共享设置。它同样应写成策略，而不是藏在管理后台的代码分支里。标识符必须唯一、不可变、不可回收，用户名和组名这类会变的值不适合直接进策略。把 RBAC 纳入整体策略，而不是二选一：角色适合稳定授权，属性适合细粒度判断，两者通常并存。

最后一条提醒：授权查询不只为“拦截请求”。列表过滤、UI 渲染、审计和离线分析都可能需要问 Cedar，因此实体切片的构造应做成可复用构件，而不是散落在各个端点里。这也是[授权模式](./auth-patterns.md)用“切片构造器”组织代码的原因。
