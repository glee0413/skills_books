知识全库

为什么需要 Cedar

几乎每个应用都会长出一套权限代码。最初它只是用户表上的一个 role 字段，几行 if 就能应付：

if user.role == "admin" || photo.owner_id == user.id {
    serve_photo(photo);
}

然后产品提出共享相册，运营要求按部门放行，法务要求“标记为私密的照片任何人都不能看”，客户要求多租户隔离。于是 if 变成 if 套 if，同一套判断在列表接口、详情接口、导出任务和后台脚本里各写一遍。半年后，没有人能回答一个简单问题：谁能看到这张照片？ 答案散落在十几处代码里，还得考虑每处代码的执行顺序。

Cedar 想解决的就是这个问题：把“谁能在什么条件下对什么做什么”从业务代码里拆出来，写成一种独立的、可读、可分析、可审计的语言。

认证回答“你是谁”，授权回答“你能做什么”

这两个词经常被混用。认证（authentication）验证主体确实是它声称的那个人，手段是密码、令牌、多因素设备。授权（authorization）则在身份已经确定之后，判断这个身份提出的这次请求是否被允许。

Cedar 只做后一半。当用户通过认证，应用就把他当作一个主体（principal），然后拿着这个主体、他想执行的动作、他想操作的对象，去问 Cedar 要一个答案。Cedar 官方文档在术语表里把这条边界写得很清楚：授权以认证为前提，但 Cedar 不参与认证。

Cedar 是什么

用一句话说：Cedar 是一门用来编写和执行授权策略的语言，附带一个授权引擎。应用把策略交给它，把每次请求的上下文交给它，它返回 Allow 或 Deny。

一段策略读起来接近自然语言：

permit (
    principal == User::"alice",
    action == Action::"view",
    resource in Album::"jane_vacation"
);

这段策略的意思是：alice 可以查看 jane_vacation 相册里的照片。注意 resource in Album::"jane_vacation"——照片不必逐张列出，只要它在相册的层级里就算命中。这种“按关系而不是按清单授权”的能力，是手写 if 很难维护的。

Cedar 项目给自己的定位有三个关键词：表达力（原生支持 RBAC 和 ABAC 这类常见模型）、性能（策略结构可被索引，实时判断延迟有界）、可分析（为自动化推理而设计，可以证明策略符合预期）。更关键的一点是策略与代码分离：策略可以被独立编写、修改、分析和审计，改一条规则不需要重新发布服务。

Cedar 不是什么

把边界划清楚，能省掉很多误用：

  • 不是认证系统。 它不校验密码、不签发令牌、不管理会话。你必须在调用 Cedar 之前完成身份验证。
  • 不是数据库。 它不存储用户、相册和照片。实体数据由应用在每次请求时提供，Cedar 只做判断。
  • 不是权限管理后台。 策略的增删改查、界面、审批流属于上层产品（例如 Amazon Verified Permissions），Cedar 本身只定义语言和引擎。
  • 不是通用编程语言。 它没有循环、没有 IO，有界大小的策略保证终止且无副作用。这是特性，不是缺陷：正因为它不能做别的事，才能被形式化分析。
  • 不负责执行。 Cedar 返回决策，真正拦截请求、隐藏字段、拒绝写入的是你的应用。拿到 Deny 却照常返回数据，Cedar 帮不了你。

默认拒绝，拒绝优先

Cedar 的合并规则只有三条，却决定了整套策略的写法：

  1. 任何一条 forbid 命中，结果就是 Deny；
  2. 否则，任何一条 permit 命中，结果就是 Allow；
  3. 都没有命中，结果是 Deny。

第一条和第三条合起来意味着：空策略库拒绝一切。访问权限只能由 permit 显式授予，不能靠“没有禁止”推断出来。第一条还意味着 forbid 是一道护栏，任何 permit 都翻不过去：

// Only the owner can access any resource tagged "private"

forbid ( principal, action, resource )
when { resource.tags.contains("private") }    // assumes that resource has "tags"
unless { resource in principal.account };     // assumes that principal has "account"

这条策略没有限定主体、动作和资源，它对所有请求生效，只在资源带 private 标签、且请求者不属于资源所在账户时拒绝。写它的人不需要知道现有或将来会有哪些 permit，因为它永远优先。

这正是 Cedar 想要的阅读体验：读 permit 时只需理解它授予了什么，不必操心它“没有禁止什么”；读 forbid 时可以独立理解，不必顺着其他策略推演。授权逻辑最难维护的部分，往往是那些“因为某处没写所以放行”的隐含路径，Cedar 从语言层面把它们消掉了。完整的合并算法和出错处理见授权如何工作。

什么时候值得用 Cedar

适合引入 Cedar 的信号通常长这样：

  • 权限是细粒度的，取决于资源归属、组成员、标签、时间或 IP，而不是一个全局角色；
  • 系统是多租户的，租户之间必须硬隔离，且租户内还有自己的管理员；
  • 权限规则会被非开发者审查，需要能拿着文本逐条讨论；
  • 出问题时需要证据：这次为什么放行、哪条策略起了作用；
  • 规则变化频繁，希望改配置而不是改代码、发版本。

反过来，如果整个系统只有“管理员”和“普通用户”两个布尔位，也没有审计和演进压力，几张表加一个中间件就够了。引入 Cedar 需要建模实体、写 schema、接 SDK，这笔投入要在规则复杂到 if 开始失控时才划算。
