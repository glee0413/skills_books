# 安全模型与最佳实践

Cedar 能替你算出 Allow 或 Deny，但不能替你决定“谁应该被允许做什么”。这一章把官方安全文档和最佳实践拆成可以落地的检查项：哪些责任在 Cedar，哪些在你的应用；默认拒绝、拒绝优先和错误跳过各意味着什么；schema、输入边界和策略存储分别防住哪类事故；以及为什么认证不能交给 Cedar。

## 共享责任：Cedar 保证求值，你保证模型

Cedar 团队对“引擎是否正确”负责：语义有一个 Lean 形式模型，生产实现用 Rust 的安全子集编写，另有差分测试保证模型和实现一致。应用团队对“策略是否正确表达业务”负责：选对实体、写对条件、给引擎提供完整且可信的数据。验证器能告诉你策略与 schema 一致，但不能告诉你 schema 本身是否漏掉了某个角色，也不能告诉你业务上该不该允许。

这就是共享责任的边界。把 Cedar 当成“授权编译器”而不是“安全部门”：它能保证同样的输入总得到同样的判定，但输入的建模权和策略的审批权仍在应用侧。

## 默认拒绝、拒绝优先与错误跳过

Cedar 的组合语义有三条，写策略前必须记住：

- **默认拒绝**：没有任何 `permit` 命中时，结果是 Deny。
- **拒绝优先**：只要有一条 `forbid` 命中，无论多少 `permit` 命中，结果都是 Deny。
- **错误跳过**：某条策略求值出错时，该策略在本次判定中被忽略。

前两条让“先放开、再用 forbid 收口”成为可行模式。例如文档云用一条全局 `forbid` 保证私有文档只有 owner 能访问：

```cedar
forbid (principal, action, resource)
when
{
  resource has owner &&
  principal != resource.owner &&
  resource has isPrivate &&
  resource.isPrivate
};
```

第三条最容易被忽视。出错的 `permit` 被忽略只会让结果更保守；出错的 `forbid` 被忽略却可能把本该拒绝的请求放行。`resource has owner` 这样的存在性检查不是装饰，它决定了策略在缺属性时是“安全地不匹配”还是“出错后被跳过”。用 schema 验证和实体校验，尽量让运行时错误根本不会发生。

## 用 Schema 把错误挡在运行时之前

Schema 声明实体类型、属性、父子关系和每个动作允许的主体/资源类型。策略通过验证后，只要实体和请求符合 schema，就不会因为类型或属性问题在运行时出错。验证器能抓的典型错误包括：

- 实体类型或动作名拼错，例如把 `Album` 写成 `Albom`；
- 动作被应用到不支持的主体或资源，例如让 `Photo` 去 `View` 一个 `User`；
- `in` 或 `==` 用错类型，例如 `principal in Album::"trip"`，但 principal 不可能是 `Photo`；
- 属性名拼错或类型不匹配，例如 `principal.jobLevel` 写成 `principal.jobbLevel`，或拿日期加整数；
- 可选属性没做存在性检查就使用，例如直接写 `principal.optionalValue < 100`；
- 扩展类型构造参数非法，例如 `IP("3.45.1111.43")`。

验证通过不等于授权模型正确，但它把“语法上就不可能成立”的策略挡在了策略库外。除了策略验证，Cedar 还提供实体验证和请求验证，用来确认运行数据符合 schema；生产环境应在写入策略和构造请求两个环节都调用。验证器的工作方式见 [策略验证](../../catalog/cedar-docs/validation.md)。

## 输入边界：长度也是安全参数

Cedar 规范不限制策略、schema 或请求的大小。对接受外部输入的策略管理系统，这意味着攻击者可以用超长策略消耗内存和解析时间。做法很直接：在进入 Cedar 之前给策略源码、schema、实体 JSON、context 设上限；只接受有界输入，再交给 Cedar 的解析器。Cedar 的策略保证终止且没有副作用，所以在有界前提下，解析和求值是安全的。

策略求值本身没有 I/O，也不会让一条策略影响另一条策略，但这不等于“可以随便执行用户提交的策略”。超长策略仍会带来存储和性能成本，动态策略数量也可能拖慢判定。长度限制、数量限制和超时应该和授权服务一起设计。

## 最小权限、策略存储与集中授权

最小权限是老话，但在 Cedar 里有一个具体含义：每条 `permit` 的范围应尽量窄，能用 `principal in Group::"support"` 就不要写 `principal`，能用具体 action 就不要用 `action` 通配。范围越窄，策略被误改或误链接时的影响面越小。

策略、实体和 context 都是授权决策的输入，必须防止被攻击者读取或修改。策略库的写权限应独立于业务应用；策略变更要走代码审查和测试，而不是让前端直接调用“新增策略”接口。若确实要让用户提交策略，至少限制长度、隔离存储、记录审计日志，并默认只让受信任的管理员启用。

官方还建议把授权逻辑集中放在 Cedar 策略里，不要一部分写在策略、一部分散落在业务 `if` 中。业务代码只负责构造请求和执行决策；否则审计时无法从策略库还原真实权限。模板是把重复逻辑收拢到一个位置的工具，也减少了“复制粘贴后漏改一处”的风险。

## 唯一不可变 ID，以及为什么不能拼接策略

实体 id 必须是唯一、规范化、不可变、不可回收的。用户名、组名、邮箱都会变，也可能被后来者复用。假设策略写的是：

```cedar
permit (principal == User::"alice",action in ...,resource in ...);
```

Alice 离职后，另一个 Alice 入职并复用了 `alice` 这个用户名，她就会继承所有残留策略的权限。正确做法是用 UUID、序列号或 URN：

```cedar
permit (
    principal == User::"2dad2883-cba1-4a1e-b212-a6c0a5290dad", // "Alice"
    action in ...,
    resource in ...
);
```

动态创建策略时，更危险的是字符串拼接。下面这种写法看似方便：

```cedar
let src = "permit (" + input + ", action == Action::\"view\", resource) when { principal.level > 3 }";
let policy = parse(src);
addToPolicySet(policy);
```

如果 `input` 是 `principal == User::"alice"`，结果符合预期；如果攻击者把它设成 `principal,action,resource); //`，拼出来的策略就变成对所有人、所有动作、所有资源的放行。即使 Cedar 保证不执行任意代码，注入 Cedar 语法本身就足以改变授权结果。用模板和参数绑定，不要让任何外部字符串进入策略源码。

## 认证是前置条件，不是 Cedar 的职责

Cedar 做的是授权：判断一个已经认证的主体能否对资源执行动作。它不做认证：不校验密码、不验证 token、不确认“自称 Alice 的请求”真的来自 Alice。应用必须先完成认证，再把可信的主体 id 放进请求。文档云用例把 `is_authenticated` 放进 context 并用 `forbid` 拒绝未认证请求，这是一个应用侧补丁；更稳妥的做法是认证失败时根本不调用授权服务。

同样，context 里的 IP、MFA 状态、同意记录等事实必须由可信的服务端组件填充，不能直接照抄客户端 JSON。认证回答“你是谁”，授权回答“你能做什么”；把两者混在一条策略里，通常意味着信任边界已经模糊。

把这些检查串起来：先认证，再规范化输入，用 schema 验证策略和数据，给所有输入设边界，用最小权限和不可变 ID 写策略，把策略库当生产代码管理。下一章讨论怎样用夹具、CLI、Rust 测试和 symcc 把这些保证变成可重复的验证。
