你已经拿到一份规格。这份规格应当有关联的工单，描述如何实现它。

议题跟踪器应当已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

目标是让整份规格在单个**集成分支**上实现，每个工单都按议题跟踪器关闭工作的方式解决。

工单不是一串步骤。它们是一张**任务图**，彼此之间存在阻塞关系。这意味着始终存在一个**前沿**：一批随时可以领取的工单。

与子代理之间的通信应当稀疏。主要靠**上下文指针**沟通：指向规格、工单、研究笔记和之前的 commit。不要重复指针已经能取到的信息。

**实现者子代理**应尽可能放到后台运行，以获得最大并发度。

## 步骤

1. 读规格和工单，理解任务图。

2. （可选）用一个**探索子代理**完成工单所需的探索——相关代码库文件或外部文档。确保探索子代理能保存文件——它应把 markdown 笔记保存在仓库之外的目录里，供之后所有子代理访问。这样**实现者子代理**可以专注实现而不是探索。

3. 创建集成分支。如果议题跟踪器通过 PR 关闭工作，或者用户要求，就在第 5 步第一次合并之后开一个草稿 PR（主分支上没有新 commit 的分支开不了 PR），标记为关闭该规格和相关工单。

4. 用**实现者子代理**实现每个工单，每个都在自己的 worktree、自己的分支上。每个实现者子代理：
   - 开始前确认自己的 worktree 基于集成分支，如果不是就 reset 到它上面；
   - 用 `tdd` 调用 Skill 工具来构建这个工单；
   - 报告完成之前，把集成分支的末端合并进自己的分支

5. 一个**实现者子代理**完成后，用**合并子代理**把它的工作合并进集成分支。

6. 如果这让可用工单的**前沿**发生变化，就启动更多**实现者子代理**处理新工单。这样可以获得最大并发度。

7. 所有工单完成后，在集成分支上用 `code-review` 调用 Skill 工具。由单个**实现者子代理**修复代码审查提出的所有问题。

8. 如果存在草稿 PR，把它标记为可审查。否则，按议题跟踪器关闭工作的方式逐个解决工单，并汇报集成分支。

9. 清理所有**实现者子代理**的 worktree。
