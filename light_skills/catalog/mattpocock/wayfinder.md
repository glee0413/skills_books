一个松散的想法来了，大到一次 agent 会话装不下，还裹在迷雾里：从这里到**目的地**的路还看不见。寻路是找到这条路，而不是朝目的地猛冲。这个技能把路线画成仓库议题跟踪器上的一张**共享地图**，然后一张一张处理它的**决策工单**（其解决产出的是一个决策、而不是待执行构建切片的问题），直到路线清晰。

目的地因事而异，而命名它就是画图的第一步：它塑造每一张工单。它可能是一份可交接并迭代的规格，一个必须在规划开始前锁定的决策，或者像数据结构迁移这样就地完成的改动。地图与领域无关：工程工作、课程内容，任何符合这个形状的东西都行。

## Plan, don't do

wayfinder 默认是**规划**：每张工单解决一个决策，当路已经清楚、在有人动手去做那件事之前不再剩下要决定的东西时，地图就完成了。想直接干活的冲动，通常正是你已经到达地图边缘、该交接了的信号。某次努力可以在它的**Notes**里覆盖这一点，把执行也纳入地图本身；但如果没有这样的说明，就产出决策，而不是交付物。

## Refer by name

每张地图和每张工单都是一个 issue，因此它有一个**名字**：它的标题。在人类读到的一切内容里（叙述、地图的 Decisions-so-far），都用这个名字来指代，绝不用裸 id、编号或 slug。一墙的 `#42, #43, #44` 无法辨认；名字一眼就能读懂。id 和 URL 不会消失；名字包裹着它的链接，但它们待在名字_里面_，绝不代替名字。

## The Map

地图是本仓库议题跟踪器上的一个单独 issue，带 `wayfinder:map` 标签，是权威产物。它的工单是地图的子 issue。

地图是**索引**，不是仓库。它列出已经做出的决策，并指向保存细节的工单；一个决策只存在于一个地方，即它的工单，所以地图从不复述它，只做简述并链接。

**地图、它的子工单、阻塞关系和前沿查询在物理上存放于何处，取决于具体的跟踪器。** 议题跟踪器应当已经提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。查阅跟踪器文档的“Wayfinding operations”一节，了解_这个_仓库如何表达它们。如果没有提供任何跟踪器，默认使用本地 Markdown 跟踪器。

### The map body

整张地图的低分辨率视图，每个会话加载一次。未关闭的工单**不**列在这里：它们是开着的子 issue，通过查询找到。

```markdown
## Destination

<走完这张地图是什么样子：这次努力正在寻找通往的规格、决策或改动。一两行；每个会话在挑工单之前都要先对准它。>

## Notes

<领域；每个会话都应当查阅的技能；这次努力的长期偏好>

## Decisions so far

<!-- 索引：每张已关闭工单一行，足够判断相关性，再顺着链接放大到工单里保存的细节 -->

- [<已关闭工单的标题>](link): <答案的一句话简述>

## Not yet specified

<!-- 见“Fog of war”：在范围内、但还无法开单的迷雾；随着前沿推进逐步毕业 -->

## Out of scope

<!-- 见“Out of scope”：被判定在目的地之外的工作；已关闭，永不会毕业 -->
```

### Tickets

每张工单都是地图的一个**子 issue**；跟踪器分配的 issue id 就是它的身份。它的正文是那个问题，大小按一次 100K token 的 agent 会话设定：

```markdown
## Question

<这张工单要解决的决策或调查>
```

每张工单都带一个 `wayfinder:<type>` 标签，取值是 `research`、`prototype`、`grilling`、`task` 之一（见 [Ticket Types](#ticket-types)）。`wayfinder:` 标签是地图和它的工单唯一携带的标签，绝不使用 `ready-for-agent` 这类分诊标签：它们是决策，不是实现工作。

一个会话在开始任何工作**之前**，先把工单分配给自己这个驱动地图的开发者，以此来**认领**它，这样并发的会话会跳过它。这个受理人_就是_认领：开着但未分配的工单就是未被认领的。

阻塞使用跟踪器**原生**的依赖关系：这很关键，因为它会在跟踪器自己的 UI 里_可视地_呈现前沿，让人不打开地图也能看到哪些可以接手。只有在跟踪器缺少原生阻塞时才退回正文约定。当阻塞某张工单的所有工单都已关闭时，该工单就是**已解除阻塞**；**前沿**是那些开着、未被阻塞、未被认领的子工单，即已知世界的边缘。

答案不属于正文；它在解决时被记录下来（见 [Work through the map](#work-through-the-map)）。解决工单期间产生的资产从 issue 链接过去，而不是粘贴进来。

## Ticket Types

每张工单要么是 **HITL**（human in the loop，与一个能为自己说话的人类_一起_进行），要么是 **AFK**，由 agent 独自驱动。HITL 工单只能通过那场实时交流来解决；agent 绝不代替人类那一侧（一个自问自答的追问 agent 已经破坏了这一点）。

- **Research**（AFK）：阅读文档、第三方 API 或本地资源（如知识库），以呈现某个决策正在等待的事实。由派出的子代理调用 Skill 工具的 "research" 来解决。当需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：通过做一个便宜、粗糙、具体的产物来供人反应（大纲、粗略尝试、桩，或 UI/逻辑代码），以此提升讨论的精度，调用 Skill 工具的 "prototype"。把原型作为资产链接进来。当“它应该长什么样”或“它应该怎么表现”是关键问题时使用。
- **Grilling**（HITL）：对话。默认情况。总是调用两次 Skill 工具，分别使用 "grilling" 和 "domain-modeling"。
- **Task**（HITL 或 AFK）：在做出_决策_之前必须完成的手工工作：没有要决定、做原型或研究的东西，但讨论被卡在它完成之前。注册一个服务好让它的 API 可被评判、开通访问权限、搬动数据好让它的形状可见。这是唯一会_做_事而不做决策的类型，它的价值来自解除某个决策的阻塞，而不是交付目的地。agent 能独自驱动时就独自驱动（AFK）；否则给人一份精确的清单（HITL）。工作完成时解决；答案记录做了什么，以及后续工单依赖的任何由此得到的事实（凭据位置、新 URL、行数）。

## Fog of war

地图是_刻意_不完整的：不要画你还看不见的东西。在活跃工单之外是**战争迷雾**：那些你能看出即将到来、但还无法确定的决策与调查的模糊视野，因为它们还挂在尚未解决的问题上。解决一张工单会清除它前方的迷雾，把现在可以具体化的东西逐个毕业成新工单，直到通往目的地的路清晰、不再剩下工单。

地图的 **Not yet specified** 一节就是写下那片模糊视野的地方：怀疑存在的问题、以后要回来看的区域。它是_通往_目的地的未发现前沿：这里的一切都在范围内，只是还不够清晰到能开单。视野允许写多松就写多松；它同时也是给协作者的指路牌，让他们读到这次努力正走向哪里。

**是迷雾还是工单？** 判断标准是你在现在能否精确陈述这个问题，_而不是_你现在能否回答它。

- **开成工单**：问题已经足够清晰，即使它被阻塞、你还不能动手。
- **留在 Not yet specified**：你还无法把它表述得那么清晰。不要把迷雾预先切成工单大小：它比一张工单更粗，等前沿到达时，一块迷雾可能毕业成好几张工单，也可能一张都不毕业。

**Not yet specified** 排除已经被决定的（Decisions so far）、已经是活跃工单的，以及超出范围的（下一节）。

## Out of scope

迷雾只会朝着目的地聚集。目的地确定了范围，所以超出它的工作就是**范围外**：它不是迷雾，也不属于 **Not yet specified**。它在地图上拥有自己的 **Out of scope** 一节：你有意识地排除在_这次_努力之外的工作。决定它归属的是范围，而不是清晰度。

范围外的工作永远不会毕业（前沿止于目的地），因此只有当目的地被重画时它才会回来，而且那时是作为一次新的努力，而不是接着上一程。

把某件事判定为范围外是一次定界行为，不是路线上的一个步骤。当一张已经存在的工单最终发现位于目的地之外时（画图时定错了范围，或在某次解决中暴露出来），**关闭它**（关闭的工单毫无疑问地不在前沿上），并在 **Out of scope** 一节留一行：简述加为什么出界，链接到那张已关闭的工单。它不进 **Decisions so far**，那里记录的是实际走过的路线；范围边界不是路线上的一个步骤。

## Invocation

两种模式。无论哪种，**每个会话绝不解决超过一张工单**，research 工单例外。

### Chart the map

用户带着一个松散的想法来调用。

1. **命名目的地。** 调用两次 Skill 工具，分别使用 "grilling" 和 "domain-modeling"，来确定这张地图正在寻找通往的是什么：那份规格、那个决策或那次改动。目的地确定范围，所以它要先定下来。
2. **画出前沿。** 再追问一次，这次**广度优先**：铺开整个空间，而不是在任何一条线上深入，把开放的决策和现在就能迈出的第一步浮现出来。**如果这没有浮现出任何迷雾**（通往目的地的路已经清楚，整段旅程小到一次会话就能走完），你不需要地图。停下来，问用户想怎么推进。
3. **创建地图**（标签 `wayfinder:map`）：填好 Destination 和 Notes，Decisions-so-far 留空，把迷雾草绘进 **Not yet specified**。
4. **创建你现在能具体化的工单**，作为地图的子 issue，然后在**第二遍**里接上阻塞边（issue 需要先有 id 才能互相引用）。交叉引用也在这一遍里写，用真实 id：占位的 `#<n>` 会自动链接到一个不相关的 issue。接边会把它们分到前沿和被阻塞两组；你暂时无法具体化的一切留在迷雾里：**Not yet specified** 一节。
5. **启动 research 子代理。** 对你刚创建的每张 `research` 工单，派生一个子代理，调用 Skill 工具的 "research" 来并行解决它，把发现记在一个一次性的 `research/<name>` 分支上，并从工单留下一个上下文指针。推送这个分支，但不要开 PR：它永远不会被合并。
6. 停下：画图就是一次会话的工作；它本身不解决任何问题。

### Work through the map

用户带着一张地图（URL 或编号）来调用。工单是**可选**的：如果没有指定，挑下一个决策的是你，而不是用户。

1. 加载**地图**：那份低分辨率视图，而不是每张工单的正文。
2. 选工单。如果用户点名了一张，就用它。否则按顺序取前沿里的第一张。**认领它**：在做任何工作之前把它分配给自己。
3. 按它的 `wayfinder:<type>` 标签所指的类型来解决这张工单（见 [Ticket Types](#ticket-types)）。读标签，而不只是正文：正文从不说明类型。**按需放大**：随时取回任何相关或已关闭工单的完整正文；调用 Skill 工具使用 `## Notes` 一节点名的技能。如果有疑问，调用两次 Skill 工具，分别使用 "grilling" 和 "domain-modeling"。
4. 记录解决结果：把答案作为**解决评论**发布，**关闭**该 issue，并向地图的 Decisions-so-far **追加一个上下文指针**。
5. 添加新浮现的工单（先创建再接线）；把答案使其可具体化的任何迷雾毕业，并从 **Not yet specified** 中清除每一块毕业的迷雾，让它只作为新工单存在。如果答案揭示某张工单（这张或另一张）位于目的地之外，就**把它判为范围外**，而不是在路线上解决它。如果这个决策让地图的其它部分失效，就更新或删除那些工单。

用户可能会并行运行已解除阻塞的工单，所以要预期其它会话会同时编辑跟踪器。
