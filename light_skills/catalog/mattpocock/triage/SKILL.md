# Triage

让项目议题跟踪器上的 issue 走过一台由分诊角色构成的小型状态机。

如果这个仓库把外部 pull request 也当作一种请求入口（见议题跟踪器配置），分诊同样覆盖它们：**一个 PR 就是带代码的 issue**，使用相同的角色、相同的状态、相同的状态机，只是下面会标出几处“对 PR 而言”的差异。按跟踪器配置，把裸写的 `#42` 解析成 issue 或 PR。

分诊期间发布到议题跟踪器的每一条评论或 issue，**都必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](agent-brief.md)：如何写出耐久的 agent 简报
- [OUT-OF-SCOPE.md](out-of-scope.md)：`.out-of-scope/` 知识库如何运作

## Roles

两个**分类**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：等待维护者评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：已完整规格化，可以交给离线的 agent
- `ready-for-human`：需要人来实现
- `wontfix`：不会被处理

对 PR 来说，同样的状态是针对附带代码来读的：`ready-for-agent` 表示已附上简报，agent 应当在 diff 上推进下一步；`ready-for-human` 表示它已经可以由人合并。

每个完成分诊的 issue 都应当恰好带一个分类角色和一个状态角色。如果状态角色互相冲突，先把它标出来并询问维护者，再做别的事。

这些是规范的角色名。议题跟踪器里实际使用的标签字符串可能不同。它们的映射应当已经提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

状态转移：没有标签的 issue 通常先进 `needs-triage`；从那里再进入 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复之后，`needs-info` 回到 `needs-triage`。维护者随时可以越权指定；对看起来不寻常的转移要标出来，先问再继续。

## Invocation

维护者调用 `/triage`，用自然语言描述他们想要什么。理解请求并照做。例如：

- “把所有需要我关注的东西列出来”
- “看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些已经可以让 agent 接手了？”

## Show what needs attention

查询议题跟踪器，按最旧的在前分成三个桶展示：

1. **未加标签**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次分诊记录以来报告者有活动**：需要重新评估。

当 PR 在范围内时，把外部 PR 也纳入这些桶，并在每行标注 `[PR]` 或 `[issue]`。发现流程只暴露*外部* PR（谁算外部由跟踪器配置定义），所以协作者自己正在推进的 PR 不算分诊工作。这个过滤只用于发现；被明确点名的 PR 无论作者是谁都要分诊。

显示数量，以及每条一句话摘要。让维护者来挑。

## Triage a specific issue or PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要看 diff）。解析已有的分诊记录，避免重复问已经解决的问题。用项目的领域术语表浏览代码库，遵守该领域的 ADR。针对代码库做两项检查：(a) **冗余**：按领域概念（而不只是请求的措辞）搜索该行为是否已有实现，并报告你查过的地方。如果找到了，这就是“已实现”的 `wontfix`（第 5 步）。(b) **此前拒绝**：读 `.out-of-scope/*.md`，把任何与之相似的条目提出来。

2. **给出建议。** 把你的分类和状态建议连同理据告诉维护者，并附上与该请求相关的代码库简要总结（包括它是否已经实现）。等待指示。

3. **核实主张。** 在任何追问之前，先确认这个主张站得住。对 bug，按报告者给的步骤复现。对 PR，确认 diff 确实做了它声称的事：取下来，跑相关测试或命令。报告结果：已确认（附代码路径）、失败，或信息不足（这是强烈的 `needs-info` 信号）。经过确认的核实会让 agent 简报强得多。

4. **追问（如需要）。** 如果请求需要补充成型，调用两次 Skill 工具，分别使用 "grilling" 和 "domain-modeling"，一轮一轮提问把它问清楚，同时打磨领域术语，并在决策落定时就地更新 `GLOSSARY.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发布一条 agent 简报评论（[AGENT-BRIEF.md](agent-brief.md)）。
   - `ready-for-human`：结构与 agent 简报相同，但说明为什么不能委派（需要判断、需要外部访问、属于设计决策、需要手动测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - 对 `wontfix`，关闭 issue，评论内容取决于*原因*：
     - **已实现**：代码库里已经有这个改动了。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库只收*被拒绝*的请求，不收已建成的）。
     - **拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论里链接过去，然后关闭（[OUT-OF-SCOPE.md](out-of-scope.md)）。
   - `needs-triage`：打上该角色。如果有部分进展，可选地留一条评论。

## Quick state override

如果维护者说“把 #42 移到 ready-for-agent”，相信他们，直接打上该角色。先确认你即将做什么（角色变更、评论、关闭），然后执行。跳过追问。如果没有经过追问就直接移到 `ready-for-agent`，问他们是否想写一份 agent 简报。

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把追问期间解决的一切都记在“established so far”下面，这样工作不会丢失。问题必须具体、可执行，不能写成“请提供更多信息”。

## Resuming a previous session

如果该 issue 或 PR 上已有先前的分诊记录，先读它们，检查报告者是否回答了任何悬而未决的问题，并在继续之前呈现更新后的全貌。不要重复问已经解决的问题。
