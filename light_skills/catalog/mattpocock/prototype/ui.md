# UI 原型

在同一个路由上生成**几个截然不同的 UI 变体**，通过底部浮动栏切换。用户在浏览器里来回翻转，选一个（或者从每个里各偷一点），然后把其余的扔掉。

如果问题关于逻辑 / 状态，而不是某样东西长什么样，那这是错误的分支。用 [LOGIC.md](logic.md)。

## 什么时候这是正确的形状

- “这个页面应该长什么样？”
- “我想在定下来之前看看这个仪表盘的几个选项。”
- “给设置页试试另一种布局。”
- 任何用户本来要在脑子里花一天在三个模糊的线框之间做选择的时刻。

## 两种子形态：强烈优先子形态 A

当一个 UI 原型**紧挨着应用的其他部分**时，判断起来容易得多：真实的头部、真实的侧栏、真实的数据、真实的密度。一个孤立的可丢弃路由是真空：每个变体在隔离状态下都看着不错。只要有合理的现有页面可以承载变体，就默认用子形态 A。只有当原型确实没有近旁的家时，才用子形态 B。

### 子形态 A：对现有页面的调整（首选）

路由已经存在。变体渲染在**同一个路由**上，由 `?variant=` URL 查询参数控制。现有的数据获取、参数和鉴权全部保留。只有渲染部分被替换。这是默认做法；除非有具体理由不这么做，否则选它。

如果原型针对的东西还没有页面，但*自然会住在某个页面里*（仪表盘的新区块、设置页的新卡片、现有流程里的新步骤），它仍然属于子形态 A。把变体挂载在宿主页面里。

### 子形态 B：新页面（最后手段）

只有当被做原型的东西确实没有现有页面可以容纳时才用它（例如一个全新的顶层界面，或者一个无法合理嵌入任何地方的流程）。

创建一个**可丢弃路由**，遵循项目已有的路由约定。不要发明新的顶层结构。命名要让人一眼看出是原型（例如在路径或文件名里包含 `prototype` 一词）。同样用 `?variant=` 模式。

在确定用子形态 B 之前，先做一次理智检查：真的没有现有页面可以嵌入吗？空路由会掩盖有内容的路由本会暴露的设计问题。

两种子形态里，底部浮动栏完全一样。

## 过程

### 1. 陈述问题并选定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音，所以封顶在这里。

把计划写成一行，放在原型所在位置或文件顶部注释里：

> “设置页的三个变体，通过 `?variant=` 切换，挂在现有的 `/settings` 路由上。”

无论用户是否在场提出反对，这都管用。

### 2. 生成截然不同的变体

为每个变体起草。每个都要满足：

- 页面的目的，以及它能访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，随便什么）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、不同的信息层次、不同的主要操作入口，而不只是颜色不同。三个略微调整的卡片网格不是 UI 原型，是壁纸。如果两个草稿出来太像，就重做一个，并明确写上“不要用卡片网格”的指引。

### 3. 把它们接起来

在路由上创建一个切换组件：

```tsx
// 伪代码，请适配项目的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：把所有现有的数据获取保留在切换器之上；只有渲染的子树随变体变化。

对于子形态 B（新页面）：`/prototype/<name>` 下的可丢弃路由挂载同一个切换器。

### 4. 构建浮动切换栏

屏幕底部居中一条小的固定定位栏，包含三部分：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体 key，如果变体导出了名字，也显示那个名字。例如 `B (Sidebar layout)`。
- **右箭头**：向前切换（循环）。

行为：

- 点击箭头会更新 URL 查询参数（用框架的路由器，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），让变体可分享、刷新后保持。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 视觉上与页面区分开（例如高对比度的胶囊、轻微的阴影），让人明显看出它不是被评估设计的一部分。
- 在生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查做门禁，这样一次误合并也不会把这条栏发给用户。

把切换器放在一个共享组件里，让两种子形态都能复用。放在项目里共享 UI 所在的位置。

### 5. 交给对方

把 URL（以及 `?variant=` 的 key）给出来。用户有空时会翻一遍。有意思的反馈通常是**“我想要 B 的头部配 C 的侧栏”**，那才是他们真正想要的设计。

### 6. 留存答案并清理

某个变体胜出后，先留存答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 描述的方式留存原型。把胜者折叠进真实代码，把其余的移到可丢弃分支，而不是 main：

- **子形态 A**：把胜者折叠进现有页面；从 main 里删掉落选的变体和切换器。
- **子形态 B**：把获胜变体提升为真实路由；从 main 里删掉可丢弃路由和切换器。

完整的变体集合是一手资料，所以它落在可丢弃分支，而不是垃圾桶，因为留在 main 分支的变体组件和切换器会很快腐烂，并让下一个读者困惑。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上有分歧。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就毁了意义。每个变体都应该能自由地扔掉布局。
- **把变体接到真实的写操作上。** 只读原型没问题。如果某个变体需要写入，就指向一个桩：问题是“这应该长什么样”，不是“后端能不能工作”。
- **把原型直接提升到生产。** 变体代码是在原型约束下写的（没有测试、最少的错误处理）。折叠进来时要好好重写。
