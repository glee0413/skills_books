议题跟踪器：GitHub

这个仓库的议题（issue）和规格（spec）都以 GitHub issue 的形式存在。所有操作都使用 gh CLI。

约定

  • 创建 issue：gh issue create --title "..." --body "..."。多行正文用 heredoc。
  • 读取 issue：gh issue view <number> --json number,title,body,labels,comments。
  • 列出 issue：gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'，并配上合适的 --label 和 --state 过滤条件。
  • 把某个 issue 变成父 issue 的子 issue：gh issue create --parent <parent> ...，或者事后执行 gh issue edit <parent> --add-sub-issue <child>（gh 2.94+）。旧版 gh 用：gh api --method POST repos/<owner>/<repo>/issues/<parent>/sub_issues -F sub_issue_id=<child-db-id>（这里是数据库 id，见下面的 阻塞（Blocking））。如果无法使用子 issue，就在子 issue 正文顶部写上 Part of #<parent>。
  • 评论 issue：gh issue comment <number> --body "..."
  • 添加 / 移除标签：gh issue edit <number> --add-label "..." / --remove-label "..."
  • 关闭：gh issue close <number> --comment "..."

从 git remote -v 推断仓库；在克隆目录里运行时，gh 会自己完成这一步。

把 Pull Request 当作分诊面

把 PR 当作请求面：否。 （如果这个仓库把外部 PR 当作功能请求，就改成 yes；/triage 会读取这个开关。）

当设置为 yes 时，PR 会走和 issue 相同的标签与状态，使用对应的 gh pr 命令：

  • 读取 PR：gh pr view <number> --comments，看 diff 用 gh pr diff <number>。
  • 列出待分诊的外部 PR：gh api --paginate 'repos/{owner}/{repo}/pulls?state=open' --jq '.[] | select(.author_association | IN("OWNER","MEMBER","COLLABORATOR") | not) | {number, title, author: .user.login, author_association, labels: [.labels[].name]}'。
  • 评论 / 加标签 / 关闭：gh pr comment、gh pr edit --add-label/--remove-label、gh pr close。

GitHub 的 issue 和 PR 共用同一个编号空间，所以光看 #42 分不清是哪一个：先用 gh pr view 42 解析，失败再退回 gh issue view 42。

寻路（wayfinding）操作

供 /wayfinder 使用。地图（map） 是一个单独的 issue，子（child） issue 就是工单。

  • 地图：一个打了 wayfinder:map 标签的 issue，正文承载 Notes / Decisions-so-far / Fog 三部分。gh issue create --label wayfinder:map。
  • 子工单：通过 GitHub 子 issue 关联到地图的 issue（见 把某个 issue 变成父 issue 的子 issue）。如果没启用子 issue，就把子 issue 加进地图正文的任务列表，并在子 issue 正文顶部写 Part of #<map>。标签：wayfinder:<type>（research/prototype/grilling/task）。一旦被认领，工单就指派给驱动它的开发者。
  • 阻塞：GitHub 的原生 issue 依赖，这是规范的、界面上可见的表达方式。用 gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id> 添加一条边，其中 <blocker-db-id> 是阻塞者的数字数据库 id（gh api repos/<owner>/<repo>/issues/<n> --jq .id，不是 #number，也不是 node_id）。GitHub 会报告 issue_dependencies_summary.blocked_by（只含未关闭的阻塞者，也就是实时门禁）。如果依赖功能不可用，就退回在子 issue 正文顶部写一行 Blocked by: #<n>, #<n>。当所有阻塞者都已关闭时，工单即解除阻塞。
  • 前沿查询：列出地图下未关闭的子 issue（gh issue list --state open，范围限定为地图的子 issue / 任务列表），剔除那些有未关闭阻塞者（issue_dependencies_summary.blocked_by > 0，或 Blocked by 行里还有未关闭 issue）或已有指派的；在地图顺序里排第一的胜出。
  • 认领：gh issue edit <n> --add-assignee @me，这是本会话的第一次写入。
  • 解决：gh issue comment <n> --body "<answer>"，然后 gh issue close <n>，最后往地图的 Decisions-so-far 里追加一条上下文指针（要点 + 链接）。
