诊断 bug

一套对付难 bug 的纪律。只有在明确说明理由时才跳过某个阶段。

探索代码库时，读 GLOSSARY.md（如果存在），建立相关模块的清晰心智模型，并检查你正在触碰那片区域的 ADR。

抹除敏感信息

这个技能会让你展示命令、输出和被捕获的产物。先抹掉每一个 secret：在原处写 <REDACTED>。把回路建立在环境变量上，这样凭据留在环境里，而不是出现在你展示的内容里。被捕获的产物带着认证头：只引用承载信号的那几行。

如果抹除后的输出不足以诊断这个 bug，就说出来并问用户。

阶段 1：建立反馈回路

这就是这个技能本身。 其余一切都是机械活。如果你有这个 bug 的紧密通过/失败信号（一条在这个 bug 上会变红的信号），你就能找到原因；二分、假设检验和插桩都只是在消耗它。如果你没有，盯着代码看再久也救不了你。

把不成比例的力气花在这里。要激进。要有创造性。拒绝放弃。

构建回路的方式，大致按这个顺序

  1. 在能触达这个 bug 的任何接缝上写一个失败测试：单元、集成、e2e。
  2. 对着运行中的开发服务器跑 curl / HTTP 脚本。
  3. 用一个固定输入做 CLI 调用，把 stdout 与已知良好的快照做 diff。
  4. 无头浏览器脚本（Playwright / Puppeteer），驱动 UI 并对 DOM/console/network 做断言。
  5. 重放捕获的 trace。 把一个真实的网络请求 / payload / 事件日志存到磁盘，再把它在隔离状态下重放进那条代码路径。
  6. 一次性 harness。 启动系统的最小一个子集（一个服务、mock 掉的依赖），用一次函数调用跑通这个 bug 的代码路径。
  7. 性质 / 模糊测试回路。 如果这个 bug 是“有时输出错误”，跑 1000 个随机输入，找那个失败模式。
  8. 二分 harness。 如果 bug 出现在两个已知状态之间（提交、数据集、版本），把“在状态 X 启动、检查、重复”自动化，这样你就能用 git bisect run 跑它。
  9. 差分回路。 把同一个输入分别跑过旧版本与新版本（或两套配置），diff 输出。
  10. HITL bash 脚本。 最后的手段。如果必须由人来点击，就用 scripts/hitl-loop.template.sh 驱动他们，这样回路仍然是结构化的。捕获到的输出会回流给你。

建对反馈回路，bug 就解决了 90%。

收紧回路

把回路当作一件产品。一旦你有了一个回路，就收紧它：

  • 我能让它更快吗？（缓存初始化、跳过无关的启动、缩小测试范围。）
  • 我能让信号更锐利吗？（断言具体症状，而不是“没崩”。）
  • 我能让它更确定吗？（固定时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒的偶发回路比没有回路只好一点点；一个 2 秒的确定性回路才是紧密的，是调试的超能力。

非确定性的 bug

目标不是干净的复现，而是更高的复现率。把触发器循环 100 次、并行化、加压力、缩小时间窗口、注入 sleep。一个 50% 偶发的 bug 是可调试的；1% 不是，所以持续提高频率，直到它可调试。

当你确实建不出回路时

停下来，明确说明这一点。列出你试过什么。向用户要：(a) 能复现它的那个环境的访问权限，(b) 一份抹除过的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。不要在没有回路的情况下继续去做假设。

完成标准：一条会变红的紧密回路

阶段 1 在回路紧密且能变红时完成：你能说出一条命令（一个脚本路径、一次测试调用、一个 curl），你已经至少运行过它一次（展示调用与输出，已抹除），并且它满足：

  • 能变红：它驱动真实的 bug 代码路径，并断言用户的确切症状，所以它能在这个 bug 上变红、在修好之后变绿。不是“跑起来不报错”；它必须能够抓住这个具体的 bug。
  • 确定性：每次运行同一个裁决（偶发 bug：按上面说的，固定且高的复现率）。
  • 快：是秒级，不是分钟级。
  • agent 可运行：你能无人值守地跑它；人在回路里只通过 scripts/hitl-loop.template.sh 参与。

如果你发现自己在这条命令存在之前就去读代码构建理论，停下：直接跳到假设正是这个技能要防止的失败模式。 没有能变红的命令，就没有阶段 2。

阶段 2：复现 + 最小化

运行回路。看着它在 bug 出现时变红。

确认：

  • 回路产生的是用户描述的失败模式，而不是附近恰好发生的另一个失败。错的 bug = 错的修复。
  • 失败在多次运行中可复现（或者，对非确定性 bug 而言，以足够高的频率可复现，可以作为调试基准）。
  • 你已经捕获了确切的症状（错误信息、错误输出、缓慢的耗时），以便后面的阶段验证修复确实解决了它。

最小化

一旦它变红，就把复现收缩到仍然会变红的最小场景。一次一个地砍掉输入、调用方、配置、数据和步骤，每砍一刀就重跑一次回路，只保留对失败承重的东西。

为什么值得费这个劲：最小复现缩小了阶段 3 的假设空间（剩下的可怀疑部件更少），并且会成为阶段 5 里干净的回归测试。

当剩下的每一个元素都承重时完成：去掉其中任何一个，回路就变绿。

在你既复现又最小化之前，不要继续。

阶段 3：提出假设

在测试任何一个之前，生成 3–5 个有排序的假设。只生成一个假设会锚定在第一个看似合理的想法上。

每个假设都必须是可证伪的：说出它做出的预测。

格式：“如果 是原因，那么 <改动 Y> 会让 bug 消失 / <改动 Z> 会让它更严重。”

如果你说不出这个预测，这个假设就只是一种感觉：丢弃它或把它磨锐。

在测试之前把排序后的清单给用户看。 他们常常有立刻就重排名次的领域知识（“我们刚往 #3 部署了一个改动”），或者知道他们已经排除过的假设。这是廉价的检查点，能省很多时间。不要因此阻塞；如果用户不在，就按你的排序继续。

阶段 4：插桩

每个探针都必须对应阶段 3 中的一个具体预测。一次只改一个变量。

工具偏好：

  1. 环境支持的话，用调试器 / REPL 检查。一个断点胜过十条日志。
  2. 在能区分假设的边界处打有针对性的日志。
  3. 永远不要“把一切都打日志再 grep”。

给每条调试日志打唯一前缀，例如 [DEBUG-a4f2]。最后的清理就变成一次 grep。没打标签的日志会活下来；打了标签的日志会死。

性能分支。 对性能回归，日志通常是错的。改为：先建立基线测量（计时 harness、performance.now()、profiler、查询计划），然后做二分。先测量，后修复。

阶段 5：修复 + 回归测试

在修复之前写回归测试，但前提是存在正确的接缝。

正确的接缝，是测试能在调用点按真实发生的样子跑通真实 bug 模式的地方。如果唯一可用的接缝太浅（bug 需要多个调用方时只有单调用方测试，单元测试无法复现触发 bug 的那条链），在那里写回归测试只会给出虚假的信心。

如果不存在正确的接缝，这件事本身就是发现。 记下它。代码库架构正在阻止这个 bug 被锁死。把这一点标记给下一个阶段。

如果存在正确的接缝：

  1. 把最小化后的复现变成该接缝上的一个失败测试。
  2. 看着它失败。如果你是靠改动代码或 fixture 强行制造红色的，就 diff 一份原始副本，证明改动确实落地了，再去相信它。
  3. 应用修复。
  4. 看着它通过。
  5. 对原始（未最小化的）场景重跑阶段 1 的反馈回路。

阶段 6：清理

宣布完成之前必须做到：

  • 原始复现不再复现（重跑阶段 1 的回路）
  • 回归测试通过（或者接缝的缺失已被记录）
  • 所有 [DEBUG-...] 插桩已移除（用 grep 搜那个前缀）
  • 一次性原型已删除（或移动到明显标记的 debug 位置）
  • 最终证明正确的那个假设写在提交 / PR 说明里，好让下一个调试者学到东西
