测试驱动开发

TDD 是红 → 绿的循环。这个技能是让这个循环产出值得保留的测试的参考：什么是一份好测试，测试放在哪里，有哪些反模式，以及循环的规则。每一节都适用于每一个循环：在循环之前和循环之中查阅它们，而不是循环之后。

探索代码库时，阅读 GLOSSARY.md（如果存在），让测试名称和接口词汇匹配项目的领域语言，并尊重你正在触碰区域的 ADR。

什么是一份好测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以完全改变，测试不应该变。一份好测试读起来像规格：“用户可以用有效购物车结账”准确告诉你存在什么能力，而且它在重构后仍然成立，因为它不关心内部结构。

示例见 tests.md，mock 指南见 mocking.md。

接缝：测试放在哪里

**接缝（seam）**是你测试所在的公共边界：你在这个接口观察行为，而不深入内部。测试住在接缝上，绝不针对内部实现。

只在事先商定的接缝上测试。 写任何测试之前，先写下要测试的接缝，并与用户确认。没有测试写在未确认的接缝上。你不可能测试所有东西，所以提前商定接缝，是把测试精力放在关键路径和复杂逻辑上、而不是每个边缘情况上的方式。

问：“公共接口是什么，我们应该测试哪些接缝？”给每个提议的接缝写一句说明：它能抓住什么，会漏掉什么。

当接口的形状本身存疑时（模块有多深、接缝应该在哪里、接口应该暴露什么），调用 Skill 工具加载 “codebase-design” 获取词汇。它是模块、接口、深度、接缝、适配器、杠杆和局部性这些词的共同来源，是一个供查阅的参考，不是要跑一场会话。

反模式

  • 实现耦合：mock 内部协作者，测试私有方法，或者通过侧信道验证（查数据库而不是走接口）。征兆是：重构时测试坏了，但行为没有变。
  • 同义反复：断言用代码计算期望值的同样方式重新计算（expect(add(a, b)).toBe(a + b)，手工按同样方式导出的快照，断言一个常量等于它自己），所以它按构造通过，永远不可能和代码不一致。期望值必须来自独立的事实源：一个已知正确的字面量、一个演算过的例子、规格。
  • 水平切片：先写完所有测试，再写所有实现。批量测试验证的是想象出来的行为：你测试的是东西的形状，不是用户可见的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁定了测试结构。改用垂直切片：一个测试 → 一个实现 → 重复，每个测试都是一颗曳光弹，回应上一轮循环教给你的东西。

循环的规则

  • 红先于绿。 先写失败测试，然后只写足够让它通过的代码。不要预判未来的测试，也不要添加投机性功能。
  • 一次一个切片。 每个循环一个接缝、一个测试、一个最小实现。
  • 重构不属于这个循环。 它属于审查阶段（见 code-review 技能），不属于红 → 绿的实现循环。
