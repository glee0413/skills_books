prototype mattpocock 模型可调用

为回答一个设计问题而构建可丢弃的原型，用来验证状态模型或逻辑的手感，或探索 UI 应该长什么样。

本页目录
  • 原型
  • 选择分支
  • 两个分支都适用的规则

原型

原型是为回答一个问题而写的可丢弃代码。问题决定它的形状。

选择分支

判断正在回答的是哪个问题：用用户的提示词、周围的代码，或者如果用户在旁边就直接问：

  • “这段逻辑 / 状态模型手感对吗？” → LOGIC.md。构建一个可分享的单一 HTML 文件（自由操作按钮，加上带标签页的引导式演练），把状态机推进到那些在纸上难以推理的情况，并让非开发者也能操作。
  • “这东西应该长什么样？” → UI.md。在同一个路由上生成几个截然不同的 UI 变体，通过 URL 查询参数和底部浮动栏切换。

两个分支产出的东西差别很大，所以选错就会浪费掉整个原型。如果问题确实模糊，又联系不上用户，就默认选更匹配周围代码的那个分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

两个分支都适用的规则

  1. 从第一天起就是可丢弃的，并清楚标注。 把原型代码放在它实际会被使用的地方附近（挨着它为之做原型的模块或页面），这样上下文一目了然；但命名要让随便看一眼的人也能看出它是原型，不是生产代码。对于可丢弃的 UI 路由，遵守项目已有的路由约定；不要发明新的顶层结构。
  2. 运行起来毫不费力。 UI 原型从项目任务运行器的一条命令开始：pnpm <name>、python <path>、bun <path> 等。逻辑演示是用户双击就能打开的单个 HTML 文件。无论哪种，启动都不该需要思考。
  3. 默认不做持久化。 状态放在内存里。持久化是原型正在检验的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，就连一个临时数据库或本地文件，文件名清楚写上“PROTOTYPE, wipe me”。
  4. 跳过打磨。 不要测试，不要超出“让原型能跑起来”所需的错误处理，不要抽象。重点是快速学到东西。
  5. 把状态亮出来。 每个动作之后（逻辑），或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到发生了什么变化。
  6. 完成时把它留存下来。 把任何经验证的决定折叠进真实代码，然后把原型本身作为一手资料留存：提交到一个可丢弃的分支，放在 main 之外，并在实现相关的 issue 上留一个指向该分支的上下文指针。答案也要留存（结论，以及它解决了哪个问题），写进 issue 或提交里。main 分支只保留经验证的决定。
