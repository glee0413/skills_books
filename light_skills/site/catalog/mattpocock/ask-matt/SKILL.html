Ask Matt

你不记得每一个技能，所以问。

在说明某个技能做什么、或建议跳过某一步之前，先读那个技能的 SKILL.md：这里的摘要只用于定位。

流程（flow） 是穿过这些技能的一条路径。大多数路径沿一条主流程前进，两条**接入路径（on-ramp）**汇入其中。其余的技能要么独立使用，要么是运行在底层的一层词汇。

主流程：想法 → 发布

大多数工作走这条路。你有一个想法，想把它做出来。

  1. /grill-with-docs 通过访谈把想法磨清楚。只要你在一个工作目录里工作，就从这里开始：它是有状态的，会把学到的东西留在 GLOSSARY.md 和 ADR 里。（没有工作目录？改用 /grill-me，见独立技能一节。两者运行同一个 /grilling 原语；grill-with-docs 是留下书面记录的那一个，所以只要手边有仓库可以留，它就是两者中更好的选择。）

  2. 分支：你能在对话里解决所有问题吗？ 如果某个问题需要一个可运行的答案（状态、业务逻辑、一个必须亲眼看的 UI），就绕道去做原型，两个方向都用 /handoff 衔接（原型住在自己的目录里，这正是 /handoff 的用途；见阶段边界）：

    • /handoff 出去，然后针对那个文件开一个新会话，
    • /prototype 用一次性代码回答这个问题，
    • /handoff 把学到的东西带回来，并从最初的想法线索里引用它。

  3. 分支：这是一次跨会话的构建吗？

    • 是 → /to-spec（把线索变成规格），然后 /to-tickets 把它拆成曳光弹工单，每个工单声明自己的阻塞边（blocking edges）。然后按两种方式之一处理这些工单：
      • 每个工单跑一次 /implement，每两个工单之间 /clear 上下文。在本地议题跟踪器上，那是 .scratch/<feature>/issues/ 下每个工单一个文件，手工按阻塞优先的顺序处理；在真正的跟踪器上，阻塞边变成原生的阻塞链接，于是任何阻塞项已完成的工单都可以被领取。每个工单都是自包含的，所以上一个工单的上下文可以丢弃。
      • /implement-spec 一次跑完整个规格。它把工单读成一张任务图，让实现者子代理并行跑过就绪的前沿，最后全部落到一个集成分支上。当你更愿意编排这次构建、而不是亲手驱动每个工单时，就用它。
    • 否 → 就在当前这个上下文窗口里跑 /implement。

    两条路都一样，代码是靠驱动 /tdd（一次一个红绿切片）建起来的，并以 /code-review 收尾——对 diff 做双轴审查（标准 + 规格）。/implement 每个工单都跑这两者；/implement-spec 的实现者各自驱动 /tdd，然后它对集成分支跑一次 /code-review。当你只想测试先行地构建一个具体行为、并不需要完整规格时，单独用 /tdd；想拿某个分支或 PR 对比一个固定点做审查时，单独用 /code-review。

    当工作以 pull request 形式提交时，/pr 负责组织正文：能展示这次改动的最小视觉材料、证明它可用的前后对比证据，以及单向门还是双向门的判断。它是模型可调用的，所以 agent 一旦要写 PR 就会去用它。

  4. /retro 闭合回路。一次构建之后——尤其是走得不太顺的那种——它会回看整个会话，建议改动 agent 的环境，而不是代码：导航指针、自动化检查、/code-review 执行的编码标准、引导文件、工具链。机械性的错误变成确定性检查；需要判断的地方变成编码标准。下一次构建于是从一个更好的环境开始。

上下文卫生

把第 1–3 步放在一个不中断的上下文窗口里（在 /to-tickets 之前不要压缩或清除），这样追问、规格和工单都建立在同一套思考之上。之后每次 /implement 都从工单出发、全新开始。/retro 要在它回看的那个会话里跑，趁你还没清除；清除之后，就把它指向那个会话的日志。

这件事的上限是**智能区（smart zone）**：模型仍能敏锐推理的那个窗口（最先进的模型上约 150k tokens）。如果会话在 /to-tickets 之前就接近它，不要硬撑着在退化状态下继续；在最近的阶段边界 /compact，然后接着做（见阶段边界）。

接入路径

一种会产生工作的起始情境，之后汇入主流程。

  • bug 和请求越堆越多 → /triage。它让 issue 走过分诊角色，产出 agent 可用的 issue，之后由 /implement 接手。

    分诊只针对不是你创建的 issue：bug 报告、新进来的功能请求，任何原始送达的东西。/to-tickets 产出的工单已经是 agent 可用的，所以不要分诊它们。

  • 有东西坏了 → /diagnosing-bugs。用于难的那些：一眼看不出的 bug、间歇性的偶发失败、在两个已知良好状态之间悄悄溜进来的回归。在拿到一个紧密的反馈回路（一条已经在这个 bug 上变红的命令）之前，它拒绝做理论推演，然后用回归测试来修。修复到位后，在同一个会话里跑 /retro，问是什么能预防这个 bug；如果真正的发现是没有好的接缝可以把它锁住，那就是 /improve-codebase-architecture 的活。

  • 一件巨大而朦胧的事：全新项目或一次巨大功能构建，大到装不进一个会话 → /wayfinder，这里认知负担最重的流程。当从这里到目的地的路还看不见时，它在议题跟踪器上画一张由决策工单组成的共享地图，一次解决一个，产出决策，而不是交付物，直到迷雾被推回去、路清楚了。/grill-with-docs 磨的是你能在一个会话里握住的想法，wayfinder 处理的是你握不住的那种；它更慢也更密，所以只留给这种情形，绝不用于范围清楚的功能。

    当地图清晰时，它交接，而不构建：在 /to-spec 处汇入主流程，由它把地图里相互链接的决策压缩成可执行的计划，然后照常 /to-tickets 和 /implement。把地图直接接进 /implement 会跳过这次压缩，把链接起来的细节丢掉，所以只有当这件事最终确实很小的时候，才直接去 /implement。

代码库健康

不是功能工作，只是维护。

  • /improve-codebase-architecture 在你有一点空闲、想让代码库更适合 agent 操作时运行。它发掘深化机会；挑中一个就生成一个想法，你可以带进主流程的 /grill-with-docs。它是寻找候选的普查；/codebase-design（见下）是你设计选中那一个的工作台。

底层的词汇

两个模型可调用的参考，运行在其他技能之下，各自是其词汇的唯一事实源。当问题出在词而不是流程上时，直接找它们；或者让上面的技能把它们拉进来。

  • /domain-modeling：磨利项目的领域语言：挑战一个模糊的词，拆解一个承载过多含义的词（"account" 干着三份活），把难以逆转的决策记成 ADR。它是 /grill-with-docs 驱动的那门主动纪律，用来让 GLOSSARY.md 保持是一份干净的术语表。
  • /codebase-design 是深模块词汇（module、interface、depth、seam、adapter、leverage、locality），用来设计模块的形状：在干净的接缝上，用小接口托住大量行为。/tdd 和 /improve-codebase-architecture 都说这套话。

阶段边界

阶段（phase） 是会话里的一块工作：追问、实现、QA。在两个阶段的边界上你有五个选项，在它们之间做选择是整张地图里最模糊的决策：

  • 继续（Continue）：留在原地。不花成本，也不丢东西。
  • /clear：清空窗口，前提是这里的东西对接下来无关。
  • /handoff 写一个可移植的 markdown 文件。范围很窄：只用于新的运行框架、新的目录、同事，或者在阶段中途分叉出一个旁支任务。它换来的是可移植性。
  • 子代理：把一个范围收得很紧的任务送到它自己的窗口，拿回一份报告。
  • /compact 压缩这份上下文，并用它给一个新会话做种子。它是默认选项，而不是第一个伸手去拿的，位于树的底部。

读 PHASE-BOUNDARIES.md 看那棵有序的树：五个问题、每个分支背后的理由，以及为什么一手来源的代价让继续成为要最先排除的那一个。在边界上做决定；阶段中途，要么继续，要么把剩下的拆给子代理。

独立技能

完全在主流程之外。

  • /grill-me：和 /grill-with-docs 一样毫不留情的访谈，但是无状态的：它不在本地保存任何东西，也不建 GLOSSARY.md。当你不在工作目录里工作时用它（磨一个计划、一个设计、一篇写作，任何底下没有仓库的东西）。如果你在工作目录里，改用 /grill-with-docs：它跑同样的访谈并留下书面记录，所以严格来说更好。
  • /grilling 是访谈原语本身：轮次、前沿，事实是 agent 的活，决策是你的。/grill-me 和 /grill-with-docs 是两个有名字的入口，/triage、/wayfinder 和 /improve-codebase-architecture 都在内部运行它。只有当你想要不带任何包装的访谈时，才直接用它。
  • /prototype 是一个小的一次性程序，用来回答一个设计问题：这个状态模型感觉对不对，或者这个 UI 该长什么样。一次性是对代码写法的约束，不是要销毁它的承诺：答案会折进真代码，原型本身则作为一个一手来源保留在从 main 分出的 prototype/<name> 分支上，由实现 issue 指向它。它是主流程第 2 步里的那条绕道，但任何时候只要一个设计问题很难在纸上定下来，都可以用它。
  • /research：把阅读的脚力活交给一个后台 agent：它对着一手来源调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你可以继续工作。它产出的文件是拿到主流程里、在 /grill-with-docs 处使用的东西，因为研究是喂养思考，而不是取代思考。
  • /to-questionnaire 在你被卡住的原因既不在你脑子里、也不在代码库里，而在别人脑子里时出场，它给对方写一份问卷去填。它是 /grill-me 的反面：不是就主题采访你，而是就这次发送（发给谁、你需要拿回什么）采访你，再把问题对准那个缺口。回来的东西是 /grill-with-docs 或 /to-spec 的素材。
  • /wizard 用于只有人才能做的步骤：开通基础设施、配置凭据或 CI secret、在一个不熟悉的第三方面板里点来点去、跑一次性的迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值，写进 .env 和 GitHub secrets，于是这套过程不再是你每次都要向 agent 重新解释的东西。它是模型可调用的，所以 agent 一撞到只有你能过的墙就会去用它。如果 agent 自己能做，它就该自己做；这个技能是为人确实在回路里的情形准备的。
  • /wait-what 是一条没落地的消息的纠正手段。在对话中途、在任何其他技能内部使用，agent 会用你缺失的上下文、用平实的话、用 GLOSSARY.md 的词汇，把它刚说过的东西重新讲一遍。它是事后补救；/grill-with-docs 是事前的解药，因为早点说定的共同语言才是让行话根本不出现的东西。
  • /teach：跨多个会话学一个概念，把当前目录当作有状态的工作区。
  • /writing-for-agents 是写 agent 消费的文档的参考：技能、AGENTS.md、被指向的文档。

前提

/setup-matt-pocock-skills：在第一次跑工程流程之前运行，配置其他技能所假定的议题跟踪器、分诊标签和文档布局。自定义的议题跟踪器也可以。
