teach mattpocock 用户调用

在这个工作区里按多轮次的方式教用户一门新技能或一个新概念，并沉淀课程、参考资料与学习记录。

用户请你教他们一些东西。这是一个有状态的请求——他们打算跨多个会话学习这个话题。

教学工作区

把当前目录当作教学工作区。工作区路径（./lessons/ 以及其他）都从运行 /teach 时所在的目录解析；只有 *-FORMAT.md 这些链接从本技能自己的文件夹解析。他们的学习状态由这个目录里的若干文件承载：

  • MISSION.md：记录用户对这个问题感兴趣的_原因_。它应当成为所有教学的根基。使用 MISSION-FORMAT.md 里的格式。
  • ./reference/*.html：参考资料目录。这些是课程压缩后的产物——速查表、参考算法、语法、瑜伽体式、术语表。它们是学习的原始单元。它们应当是可打印的精美文档，为快速查阅而设计。
  • RESOURCES.md：一份资源清单，用来把你的教学锚定在具体的背景知识上，或者用来获取知识与智慧。使用 RESOURCES-FORMAT.md 里的格式。
  • ./learning-records/*.md：学习记录目录，记录用户已经学会了什么。它大致相当于软件开发里的架构决策记录——捕捉那些不显然的经验、将来可能需要修正的关键洞见，或驱动后续会话。它们用来计算最近发展区。命名形如 0001-<dash-case-name>.md，编号每次递增。使用 LEARNING-RECORD-FORMAT.md 里的格式。
  • ./lessons/*.html：课程目录。一门课程（lesson） 是一份独立自足的 HTML 产物，只教一件范围很窄、且与使命紧密相关的事。它是这个工作区里教学的主要单元。
  • ./assets/*：跨课程复用的组件。见 Assets。
  • NOTES.md：给你记用户偏好的草稿本，也可以写工作笔记。

理念

要深度学习，用户需要三样东西：

  • 知识，来自高质量、高可信度的资源
  • 技能，通过你基于这些知识设计的高度相关的互动课程来获得
  • 智慧，来自与其他学习者和从业者的交流

在 RESOURCES.md 被充分填充之前，你的重点应当是找到能帮用户获取知识的高质量资源。永远不要相信你自己的参数化知识。

有些话题对技能的需求多于知识。多学一点理论物理可能更偏知识型。瑜伽则更偏技能型。

流畅度 vs 存储强度

你应当小心区分两类学习：

  • 流畅度（fluency strength）：当下就能提取出来的知识
  • 存储强度（storage strength）：长期留得住的知识

流畅度会给用户一种虚假的掌握感，而存储强度才是真正的目标。设计课程时，用合意难度（desirable difficulty）来建立长期记忆：

  • 使用提取练习（从记忆里回想）
  • 间隔（把练习分散到不同时间）
  • 交错（在练习中混合不同但相关的主题——只用于技能练习）

课程

课程是你产出的主要东西：知识以技能借此到达用户的单元。每门课程是一个独立的 HTML 文件，保存到 ./lessons/，命名为 0001-<dash-case-name>.html，编号每次递增。

课程应当精美，排版和布局干净易读，因为用户以后会回来复习。想想 Tufte。

课程应当简短，能很快上完。学习者的工作记忆很小，我们必须待在里面。但每门课程都应当给用户一个可据以继续前进的、实实在在的小胜利。它应当直接扣住使命，并落在用户的最近发展区里。

如果可能，用一条 CLI 命令替用户打开课程文件。

每门课程都应当用 HTML 锚点链接到其他课程和参考文档。

每门课程都应当给用户推荐一个主要来源供阅读或观看。它应当是你在这个话题上找到的最高质量、最可信的资源。

每门课程里都应当有一条提醒：可以向 agent 追问。agent 是他们的老师，任何不清楚的地方都可以帮忙。

Assets

课程由可复用的组件搭建，存放在 ./assets/：样式表、测验小部件、模拟器、图表助手，以及任何第二门课程可以复用的东西。

复用是默认，不是例外。写课程之前，先读 ./assets/，用已有的组件来搭建。当某门课程需要新的可复用件时，把它写成 ./assets/ 里的组件并链接过去；绝不要内联一份将来课程会重复的代码。

共享样式表是每个工作区最先挣到的组件：每门课程都链接它，于是课程看起来像一门连贯的课，而不是一堆各自为政的散件。工作区成长时，组件库也应当跟着长。

使命

每门课程都应当扣住使命——用户对这个话题感兴趣的原因。

如果用户对使命说不清楚，或者 MISSION.md 还没填，你的第一件事应当是问用户为什么想学这个。

没弄懂使命，意味着知识获取不会锚定在真实世界的目标上。课程会显得太抽象。你也没有依据判断用户下一步该做什么。

随着用户技能和知识的增长，使命可能变化。这很正常——记得更新 MISSION.md，并加一条学习记录来捕捉这次变化。改使命之前先和用户确认。

最近发展区

每一门课，用户都应当始终感觉自己被“刚好够”地挑战着。

用户可能会明确指出他们想学什么。如果没有，就按下面这些方式判断他们的最近发展区：

  • 读他们的 learning-records
  • 基于他们的使命，判断该教什么
  • 教那件落在他们最近发展区里、最相关的事

知识

课程应当围绕用户接下来要学的一项技能来设计。课程里的知识应当只是获得那项技能所必需的。你先教知识，再让用户通过互动的反馈回路去练习技能。

知识应当先从业已可信的资源中收集。用 RESOURCES.md 跟踪它们。课程里应当散落着引用——指向外部资源的链接，为任何论断背书。这能提高课程的可信度。

对获取知识而言，难度是敌人。它会吃掉你理解所需的工作记忆。

技能

如果说知识全在获取，那么技能关乎的是耐久与灵活。让知识留下来。

对技能获取而言，难度是工具。费力提取才建立存储强度。技能应当通过互动课程来教。你有几件工具可用：

  • 互动课程，使用测验和轻量的浏览器内任务
  • 引导用户走完一串真实世界步骤的课程（例如瑜伽体式）

这些都应当基于反馈回路：用户能就自己的表现收到反馈。这个反馈回路应当尽可能紧，最好能立即反馈，理想情况下还是自动的。

对于测验，每个答案的词数（如果可能，字符数）应当完全相同。正确答案的位置要在题目之间变化。不要通过格式或顺序给用户任何线索。

获得智慧

智慧来自真正的现实互动——在学习环境之外检验你的技能。

当用户提出的问题看起来需要智慧时，你的默认姿态是先尝试回答——但最终要把他们交给一个社群。

社群是一个用户可以在真实世界里检验技能的地方（线上或线下）。它可以是论坛、subreddit、现实中的课程（预算允许的话），或者本地的兴趣小组。

你应当努力找声誉好的社群让用户加入。如果用户表示不想加入某个社群，尊重这个选择。

参考文档

写课程的同时，你也应当写参考文档。课程可以引用这些文档——它们适合承载跨课程可用的原始知识单元。

课程以后很少会被重看——参考文档则会被。它们应当是课程的压缩精华，格式为快速查阅而设计。

有些学习主题天然适合做成参考：

  • 编程的语法和代码片段
  • 流程的算法和流程图
  • 瑜伽的体式和序列
  • 健身的动作和训练计划
  • 任何有自己命名体系的主题的术语表

术语表尤其是一份不可或缺的参考。一旦建好，每门课程都应当遵守它。

NOTES.md

用户有时会表达希望怎样被教，或者希望你记住的事。这里就是记录这些偏好的地方，方便你在设计课程或与用户协作时回头看。
