retro mattpocock 用户调用

对一次编码会话做复盘，提出能改进编码 agent 环境的候选改动。

本页目录
  • 步骤
  • 参考
  • 实现与审查
  • 文件

用户要求做一次复盘。你要针对编码 agent 的环境提出改进，以改善未来的运行。

步骤

  1. 用 writing-for-agents 调用 Skill 工具，获取写作风格指南。

  2. 阅读用户指定那次会话的一手资料。这可能意味着在本机搜索会话日志。如果用户没有指定会话，默认用当前这次。

  3. 在以下类别里寻找可改进的候选。

  • 导航：agent 找到正确文件有多容易？文件之间有没有隐藏依赖？一个导航指针会不会让它更容易？适用时机：这次会话花了很长时间才找到某条信息。
  • 自动检查：有没有能抓住 agent 所犯错误的自动检查？lint、类型检查、测试、文件系统 linter？先读仓库自己的检查命令（它的 package.json / 构建工具的 lint / check 脚本、它的 CI 工作流），这样如果某个检查已经存在但没接上或悄悄坏了，发现就是“它没接上”，而不是重新发明一个。一个没有护栏的仓库（没有 pre-commit hook，也没有任何 CI 任务运行它的 lint / typecheck / test 命令）本身就是一项发现：没有 lint 的仓库是一个长期错失的机会，而不是中性的默认状态。适用时机：agent 犯了一个自动检查本可以抓住的错误，或者仓库根本没有护栏。
  • 编码规范：是否应该给审查 agent 一条新规则去执行？是否应该删除或澄清某条现有规则？先给违规分类：机械性的违规（固定的语法模式、被禁的 API、某种 import 形状、文件位置规则）要用确定性检查，没有例外：仓库自有 linter 里的自定义规则、新的 pre-commit hook，或者新的 CI 任务，哪个在仓库的语言和现有护栏下最便宜就用哪个。默认是构建检查，而不是写规则。CODING_STANDARDS.md 只留给真正的判断性决定（跨文件一致性、“与周围风格一致”、任何护栏永远无法替代的东西）。适用时机：审查 agent 没能抓住某个错误。
  • 全局 AGENTS.md：有没有哪些引导指令应该移到编码规范（或自动检查）里？适用时机：AGENTS.md 文件特别大——无论是在仓库里还是在用户的全局范围。
  • 工具经济性：agent 有没有做出本可以精简的昂贵工具调用？有没有特别 token 低效的自定义工具（CLI、MCP）？适用时机：agent 做了一次昂贵的工具调用。
  • 空操作：寻找引导文件里不改变 agent 行为的指令。适用时机：引导文件又大又笨重。
  • 信息获取：寻找增加 agent 信息获取机会的方式。把开发服务器日志 tee 出来，对第三方服务做只读访问。适用时机：某条关键信息对 agent 不可用。
  1. 按严重程度把这些候选呈现给用户。

参考

实现与审查

记住所有工作都经过两个阶段：实现和审查。实现 agent 承受最大的上下文压力。它负责探索、写代码和调试失败。

审查 agent 的上下文压力最小——它收到一个 diff，所以不需要探索。它通常不需要写代码或调试。

这意味着应该由审查 agent 负责强制执行编码规范，而不是实现 agent。

文件

你可以使用仓库里的若干文件：

  • CLAUDE.md/AGENTS.md：这些文件会被推送到任何在此仓库工作的 agent 的上下文窗口。它们应该极其克制地使用，通常只用于指向其他文件的导航指针。
  • CODING_STANDARDS.md：这个文件在审查时读取，不在实现时读取。如果规范文件超过 1,000 行，就给文档文件夹加导航指针。
  • 文档：把文档当作参考文件，由其他文件指向。写新文档之前先找现有文档。
  • 技能：用技能来承载文档（因为它们的 description 会进入 agent 的上下文窗口），或者用于用户调用的命令。遵循 writing-for-agents 技能里的建议。
