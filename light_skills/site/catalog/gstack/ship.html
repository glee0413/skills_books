Ship：全自动发布工作流

STOP 会阻止推进，直到所述的修复/恢复路径被清除；没有这样的路径时，结束本次尝试。 在继续之前，逐个回答每个 AskUserQuestion。 常规授权从不会豁免这些门禁，也不会豁免它们所需的用户决策。

**常规工作不需要确认：**包括未提交的改动、在 Step 12 下选择 MICRO/PATCH、起草 CHANGELOG 和提交、标记已完成的 TODO 以及自动修复发现的问题。 当 Step 7 的覆盖率达标时，报告剩余缺口并验证生成的测试，无需再次询问。Step 15 会提交这些测试。

**路线：**整合（1–3）→ 测试与审查（4–11.5）→ 准备发布（12–15）→ 验证冻结的内容（16）→ 推送并发布（17–21）。 每次新的调用都会重复 Step 1–16，包括两次审查和文档审计。 Step 12、17 和 19 用于防止重复递增版本、重复推送和重复创建 PR，而不是防止验证。

在步骤之间保留状态

在产品目录树之外保留一份私有的 Markdown 调用记录，并保存它的绝对路径；记录使用下列标题，以便暂停的运行可以恢复：

  • **Release：**版本号、BUMP_LEVEL、已审查的目录树和尝试次数。
  • **Decisions：**每次批准的发现、涉及文件和被授权的动作。只在同一范围内复用它；修复从不重置或扩大批准范围。
  • **Reviews：**句柄、原始 start token、终态、输出和排队的修复。
  • **Checks：**命令/标签、结果/计数、时间戳、日志和消耗的输入。
  • **Documentation：**候选/id、已用尝试次数、已接受的哈希或具名的阻塞例外。
  • **Next steps：**一份有序的工作清单，并标记当前步骤。

**回执（receipt）**是一次检查的命令、结果和所消耗内容的已保存证据。 一次审查的 start token 是 gstack-review-log --start 在读取 diff 之前返回的不透明值。为 Step 9 保留 REVIEW_START，为 Step 11 的每次尝试保留单独的 PASS_START，为设计保留 DESIGN_START。每次检查都用它自己的原始 token 收尾；--finish 会自动盖住绑定字段。绝不借用或替换 token。 gstack-wtree 打印的是覆盖已跟踪文件和未被忽略的未跟踪文件的 Git 树哈希，不是 commit ID。用 git diff <old-tree> <new-tree> 比较这些快照。

Ship 控制流

运行 /ship 的你（父级）掌握推进权；子任务返回的是证据，不是继续推进的许可。遵循已保存的工作清单：

  1. 按顺序从 Step 1–21 开始，包括 6.5、11.5 和 14.5。只有当前项的各个门禁都清除后才推进。
  2. 把一次修复展开成单独的步骤，插入到仍未完成的工作之前。这替换了当前项，其结果的记录仍然保留。 只有当目标步骤还不是下一个待办步骤时才追加它。
  3. 遇到另一次修复时，重复规则 2，同时不丢弃待办工作。 已保存的清单优先于修复内部的常规“下一步”语句。 一个范围绝不追加未列出的步骤。

**示例：**Step 11 的修复把 9 → 10 → 11 插入到 11.5 之前。如果之后 Step 9 的修复又影响到 6–8，清单就变成 5 → 6 → 7 → 8 → 9 → 10 → 11 → 11.5。 未受影响的发布步骤随后继续。修复期间 STOP 和 AskUserQuestion 门禁依然生效。

在整个调用过程中保持同样的尝试计数。以 Step 14 结束的范围不会进入 Step 14.5。包含 Step 14.5 的范围进入它已有的审计决策，而不是无条件发起新的审计；它的“初始加一”上限永不重置。 被允许的修复在本次调用中继续，不重启 /ship。

Step 0：识别平台与基础分支

首先，从远端 URL 识别 git 托管平台：

git remote get-url origin 2>/dev/null
  • 如果 URL 包含 "github.com" → 平台为 GitHub
  • 如果 URL 包含 "gitlab" → 平台为 GitLab
  • 否则，检查 CLI 是否可用：
    • gh auth status 2>/dev/null 成功 → 平台为 GitHub（涵盖 GitHub Enterprise）
    • glab auth status 2>/dev/null 成功 → 平台为 GitLab（涵盖自托管）
    • 两者都不成功 → unknown（只用 git 原生命令）

确定这个 PR/MR 的目标分支；如果还没有 PR/MR，则用仓库的默认分支。在后续所有步骤中把结果当作“基础分支”。

如果是 GitHub：

  1. gh pr view --json baseRefName -q .baseRefName——成功就用它
  2. gh repo view --json defaultBranchRef -q .defaultBranchRef.name——成功就用它

如果是 GitLab：

  1. glab mr view -F json 2>/dev/null 并提取 target_branch 字段——成功就用它
  2. glab repo view -F json 2>/dev/null 并提取 default_branch 字段——成功就用它

git 原生回退（平台未知，或 CLI 命令失败）：

  1. git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's|refs/remotes/origin/||'
  2. 如果失败：git rev-parse --verify origin/main 2>/dev/null → 使用 main
  3. 如果失败：git rev-parse --verify origin/master 2>/dev/null → 使用 master

如果全部失败，回退到 main。

打印识别出的基础分支名。在后续每一个 git diff、git log、git fetch、git merge 和 PR/MR 创建命令里，凡是说明中提到“基础分支”或 <default> 的地方，都替换成识别出的分支名。

<base> 表示识别出的分支名，用于 fetch/辅助脚本参数；origin/<base> 是它用于比较的远端跟踪引用。Step 1 会 fetch 它。

Step 0.9：识别 Apple 目标

如果请求的是 App Store/TestFlight 分发，寻找 .xcodeproj、.xcworkspace 或 Swift app 产物。阅读 Package.swift 及其入口，以区分 app 与库/CLI。如果仍不清楚，用 AskUserQuestion 确认目标，并等待答案后再选择发布路径。 对确认是 app 的情况，STOP，并先阅读 ~/.claude/skills/gstack/ship/sections/apple-release.md。商店分发通过该适配器从当前分支继续，包括干净的基础分支。 下面的分支门禁和仓库落地流水线仅适用于仓库落地请求，包括发生在 Apple 仓库上的请求。

Step 1：起飞前检查

  1. 把当前分支保存为 <branch-name>。如果位于基础分支或仓库默认分支，中止：“你正在基础分支上。请从特性分支发布。”

  2. 运行 git status（绝不用 -uall）。未提交的改动总是包含在内；不要询问。

  3. 在查看 diff 之前运行 git fetch origin <base>。如果 fetch 失败，STOP： 报告错误，先恢复访问权限。然后查看 git diff origin/<base> --stat、status 中的未跟踪文件，以及 git log origin/<base>..HEAD --oneline。

  4. 用下面的看板展示历史就绪情况，然后结束 Step 1。 以往的 CLEAR 审查或看板跳过，永不替代 Step 9 的门禁。

审查就绪看板

在起飞前检查中，读取审查日志和配置以展示就绪情况；Step 9 会运行新的落地前审查。

~/.claude/skills/gstack/bin/gstack-review-read

**1. 选择要展示的记录。**下面每一行都用最新的一条记录。 不要用超过 7 天的记录来清除某一行，也绝不用更早的成功替代更新的失败。ship 指标不是审查记录。

行 取以下最新者 状态后缀
Eng Review review 或 plan-eng-review (DIFF) 或 (PLAN)
CEO Review plan-ceo-review —
Design Review plan-design-review 或 design-review-lite (FULL) 或 (LITE)
Adversarial adversarial-review 或旧版 codex-review —
Outside Voice 来自 CEO 或 Eng 审查的 codex-plan-review —

保留每条记录的 host、source、outside_provider、outside_status 和 phase。 历史来源 "claude" 是原生子代理；"claude-code" 是外部 CLI。 不要根据今天的运行框架推断旧的提供方或未知模型。原生结果不能填补缺失、已禁用或已跳过的外部覆盖。

**来源归属：**若有记录的 via 就把它追加到后缀（"CLEAR (PLAN via /autoplan)"）；没有则保留 "CLEAR (PLAN)" 或 "CLEAR (DIFF)"。在看板下方，按工作流运行和阶段分组展示 autoplan-voices 和 design-outside-voices。展示每个阶段的提供方和 outside_status；保留部分覆盖的情况。这些细节不能清除 Eng Review。

2. 在给出结论之前检查新鲜度。

  • **内容优先规则：**对 review、adversarial-review、codex-review、 ship 阶段审查和 design-review-lite，使用 review_freshness.status 并展示它的 reason。CURRENT 表示一次已完成的干净审查，其开始与结束的 内容指纹都等于当前的 ---WTREE--- 指纹。 STALE 或 UNVERIFIED 不能清除 Eng Review。缺少 review_freshness， 包括只有日志的旧记录，意味着 UNVERIFIED。绝不用 HEAD 相等或提交距离 作为 diff 证据的替代，即使提交数为零也不行。 展示已记录的 cycles、completed/converged 字段，以及缺失的来源/阶段 覆盖。未知的覆盖不是通过。
  • 计划记录（plan-ceo-review、plan-eng-review、plan-design-review 和 codex-plan-review）使用 7 天窗口，而不是工作树指纹。 如果存在 plan_sha256，可以比较计划文件并报告不一致。 把记录的提交与 ---HEAD--- 比较；如果不同，运行 git rev-list --count STORED_COMMIT..HEAD 并报告 “Note: {skill} review from {date} may be stale — {N} commits since review”。 命令失败意味着 UNKNOWN，按过期处理；没有提交跟踪时，建议重跑。所有审查都 最新时省略这些提示。

**3. 给出历史结论。**CLEARED 要求选中的 Eng Review 为 clean、在 7 天以内且 在步骤 2 下是新鲜的。否则报告 NOT CLEARED 及其缺失、过期或存在未决问题的原因。 没有 Eng Review 记录时，说明“没有保存的 Eng Review：运行只读 /plan-eng-review 打印的 PERSIST: 行，或重跑它”（docs/troubleshooting.md#plan-eng-review-not-persisted）。如果 skip_eng_review 为 true，Eng Review 展示 “SKIPPED (global)”，而本看板为 CLEARED。 这个结论绝不跳过 Step 9 及其发现、批准和收敛门禁。即使历史为 NOT CLEARED 也继续 Step 1。

其他行提供的是背景信息，不能替代 Eng Review：

  • 产品/业务或范围决策建议做 CEO Review，常规修复或清理不建议。
  • UI/UX 工作建议做 Design Review，后端、基础设施或纯提示词工作不建议。
  • 对抗性审查总是包含一次原生检查。可用且已启用的外部挑战作为补充； 200 行以上的 diff 还会走结构化的 P1 门禁。
  • Outside Voice 是 CEO/Eng 审查之后默认开启的计划审查。codex_reviews 会禁用这个额外步骤。提供方失败时使用原生回退并记录缺失的外部覆盖； 这一行永不作为发布的门禁。

**4. 展示看板。**把缺失、过期、禁用或不可用的结果显示为显式状态，绝不显示为 CLEAR。把新鲜的 clean 结果显示为 CLEAR，把 issues_open 显示为 ISSUES OPEN，同时不改变已存的状态。

REVIEW READINESS DASHBOARD

步骤 1 中的每个条目占一行。只有 Eng Review 标记为必需。

Review Runs Last run Status Required
{行与后缀} {计数} {时间戳或 —} {实际状态与原因} {yes/no}

状态为 unverified 或 unavailable 的外部审查属于覆盖缺失，绝不是通过。

对 200 行以上的 diff（git diff origin/<base> --stat | tail -1），建议 /plan-eng-review 或 /autoplan。

对 Design Review：运行 source <(~/.claude/skills/gstack/bin/gstack-diff-scope <base> 2>/dev/null)。如果 SCOPE_FRONTEND=true 且没有设计审查记录，提示：“Design Review 未运行 — Step 9 包含轻量检查；如需完整视觉审计可考虑 /design-review。”

不询问，继续 Step 2；Step 9 会应用审查门禁。

Step 2：分发流水线检查

检查新的独立产物（CLI 二进制、包、工具）的分发，已部署的 Web 服务不算。

  1. 列出候选分发路径：

    git diff origin/<base> --diff-filter=A --name-only | grep -E '(^|/)(cmd/[^/]+/main\.go|bin/[^/]+|Cargo\.toml|setup\.py|package\.json)$' | head -5

    把 Step 1 status 中匹配的未跟踪文件也算进来。逐个阅读匹配项： 单独一个新的 package.json 或 Cargo.toml 不是可发布产物； 还要检查已有清单中新声明的二进制或包导出。只有当确实存在新的 可分发包时才设门禁。

  2. 如果检测到新产物，检查是否有发布工作流：

    ls .github/workflows/ 2>/dev/null | grep -iE 'release|publish|dist'
grep -qE 'release|publish|deploy' .gitlab-ci.yml 2>/dev/null && echo "GITLAB_CI_RELEASE"

  3. **有新产物但没有流水线：**AskUserQuestion：“合并之后，没有发布流水线 用户就无法下载这个产物。”

    • A) 现在就加上该平台的发布工作流
    • B) 推迟，在 Step 14 记一条 P1 分发 TODO
    • C) 不需要：仅内部/Web 使用，已由现有部署覆盖

  4. **如果选 A：**按仓库的 CI 惯例添加打包/发布配置。 先询问未知的目标、仓库或访问凭据；绝不臆造凭据。 针对该产物再检查一遍，并把工作流纳入测试和审查。 在 /ship 期间不要发布正式版本。

  5. 否则不加流水线，继续。

Step 3：合并基础分支（在测试之前）

Step 12：版本号递增（自动决策）

条目 3 需要 BUMP_LEVEL：复用本次调用已保存的级别。否则 FRESH 在条目 2 中选择它，ALREADY_BUMPED 在条目 1 中推导它。

ship: queue_mode stamp-at-merge 会替换条目 1–4。

  1. 分类状态——纯读取，从不写入：

    bun --no-env-file --config=/dev/null run ~/.claude/skills/gstack/bin/gstack-version-bump classify --base <base>

    把 JSON 中的 baseVersion 保存为 BASE_VERSION，然后读取 state 并分派：

    • FRESH → 使用已记录的级别，或在条目 2 中选择级别，然后检查队列并写入。
    • ALREADY_BUMPED → 保持 NEW_VERSION=currentVersion。如果缺少 BUMP_LEVEL， 就取 baseVersion 到 currentVersion 之间第一个变化的组件 （major/minor/patch/micro；不存在的第四段视为零）。继续条目 3， 而不是再做一次自动递增。
    • DRIFT_STALE_PKG → 运行 gstack-version-bump repair，然后重新分类。 成功则按 ALREADY_BUMPED 处理，包括它的队列检查；失败则停止。 仅靠修复永不再次递增版本。
    • DRIFT_UNEXPECTED → STOP：package.json 与 VERSION 不一致，而 VERSION 与基础分支一致。先处理这处手工编辑，再重新分类。
    • NO_VERSION → 逐字打印 notice，并在不做版本变更的情况下 ship：跳过 Step 12 的剩余部分和 Step 13 的 CHANGELOG 条目，绝不创建 VERSION，在 Step 18 使用 无前缀的标题，并在 Step 20 记录 "version":null。
    • 退出码 2 → STOP 并展示 stderr：所配置的版本文件缺失、为空、 不可读或格式错误。修复它或它的固定配置，然后重新分类。绝不用 0.0.0.0 顶替。

  2. 根据 diff 决定递增级别（由 agent 判断）：

    • MICRO：少于 50 行，琐碎的调整/配置。PATCH：50 行以上，没有功能信号。
    • MINOR：出现任何功能信号（新路由/页面、迁移、模块）或 500 行以上时询问。 MAJOR：出现里程碑或破坏性变更时询问（ship: bump patch 永不询问）。 AskUserQuestion：带理由的推荐级别、更小的级别，或取消。 等待；取消会在发布写入或推送之前停止，并保留现有工作。 用小写的 BUMP_LEVEL 保存。声称的版本号可以把下一个可用号往前推， 但不能改变已选的 MICRO/PATCH/MINOR/MAJOR 级别。

  3. 队列感知的挑选：

    QUEUE_JSON=$(bun --no-env-file --config=/dev/null run ~/.claude/skills/gstack/bin/gstack-next-version --base <base> --bump "$BUMP_LEVEL" --current-version "$BASE_VERSION" 2>/dev/null || echo '{"offline":true}')
CANDIDATE_VERSION=$(echo "$QUEUE_JSON" | jq -r '.version // empty')

    **先判定是否合格：**要求工具输出成功，且版本号非空并有效。 offline:false 合格；offline:true 只有在带 fallback:"git" 时才算合格。 离线输出缺少该回退、命令失败、输出格式错误或版本号为空 都不可用，即使其中含有看起来像版本号的字符串。

    不完整（complete:false）：unknown_claims 中的 PR 未被读取；挑选可能 撞车。重跑条目 3 一次；仍然不完整则 AskUserQuestion：使用它（推荐； Version Gate CI 会重读队列）还是停止。

    • **可用候选：**打印警告和已声称的队列。FRESH 设置 NEW_VERSION=CANDIDATE_VERSION。 ALREADY_BUMPED 把它与 currentVersion 比较：若不同，询问是重新递增 （刷新 CHANGELOG/PR 标题）还是保持当前值（CI 会拒绝冲突）。 只有获得批准才改变既有版本。按 branch 和 version 检查 JSON 的 active_siblings；持有 >= NEW_VERSION 的兄弟分支需要做出选择： 越过它，或结束本次尝试并同步。
    • **没有可用候选：**打印 queue-unverified。FRESH 用本地 BUMP_LEVEL 算术；ALREADY_BUMPED 保持 currentVersion。绝不用空候选。

  4. 写入递增（FRESH，或获得批准的重新递增）：

    bun --no-env-file --config=/dev/null run ~/.claude/skills/gstack/bin/gstack-version-bump write --version "$NEW_VERSION" --regen-digest --changelog CHANGELOG.md

    它会写入 VERSION、清单和锁文件，并把 ## [Unreleased] 移到 NEW_VERSION 下 以供 Step 13 使用。退出码 2 表示什么都没写：展示 stderr，停止。 退出码 3 是半写入：重新分类并对 DRIFT_STALE_PKG 执行 repair。

    --regen-digest 只在 scripts/gen-agents-digest.ts 和已提交的 agents-digest/gstack-AGENTS.md 都存在时才运行它；如果 agentsDigest 为 false，运行 bun --no-env-file --config=/dev/null scripts/gen-agents-digest.ts 并把摘要随递增一起暂存。推送之前， 验证已提交的摘要与所选 VERSION 的生成结果一致。

  5. 在版本已写入之后记录发布决策，包括获得批准的 ALREADY_BUMPED 重新递增。跳过未变化的版本和只修清单的修复。

    ~/.claude/skills/gstack/bin/gstack-decision-log '{"decision":"Ship NEW_VERSION (BUMP_LEVEL)","rationale":"WHY","scope":"repo","source":"skill","confidence":9}' 2>/dev/null || true

    替换 NEW_VERSION、BUMP_LEVEL 和一行 WHY（范围或破坏性变更信号）；尽力而为。

**STOP。**在撰写 CHANGELOG 条目（Step 13）之前，阅读 ~/.claude/skills/gstack/ship/sections/changelog.md 并完整执行。 不要凭记忆工作——那一节才是这一步的事实来源。

5. 先报告，再推送

只提交 Step 15 之后仍未提交、且已批准并已验证的发布改动， 包括生成产物；使用它的分组规则；绝不创建空提交。 保留无关的用户文件。

贴出构建/文档/测试结果。豁免只可用于同样的、已验证的既有失败和已批准范围；引用实际的批准和失败 计数，绝不用 FRESH 或全绿。新增、变化或未被豁免的测试失败按 阶段 4 的恢复流程处理，然后才发布。

然后是诚实清单，两行，来自 Step 9 最新的 Gate edits: 行 及其记录：

  • 对每个门禁发现：gate、路径、处置（kept/restored/open）、 reason 和记录器盖章的 actor。如果没有，则写覆盖行 （none detected (...)、partial (...) 或 UNAVAILABLE — ...）。
  • 每条测试泳道的 tests_ran（N、ZERO-RUN 或 count unavailable）。 以审计者的姿态写这份报告：本次会话自身的门禁编辑是供读者审视的证据， 不是需要辩护的立场；被保留的门禁只陈述理由，别的都不写。否则继续 Step 17。

Step 17：推送

凭据推送前守卫——在推送之前运行：

_REDACT_PREPUSH=$(~/.claude/skills/gstack/bin/gstack-config get redact_prepush_hook 2>/dev/null || echo "false")
_HOOK_PATH=$(git rev-parse --git-path hooks/pre-push 2>/dev/null || echo "")
_HOOK_STATE="missing"
if [ -e "$_HOOK_PATH" ] || [ -L "$_HOOK_PATH" ]; then
  _HOOK_STATE="unmanaged"
  if [ -f "$_HOOK_PATH" ] && [ ! -L "$_HOOK_PATH" ] && grep -Fqx '# gstack-redact pre-push (managed)' "$_HOOK_PATH" 2>/dev/null; then
    _HOOK_STATE="managed"
  fi
fi
_HOOKS_DIR=$(git rev-parse --git-path hooks 2>/dev/null || echo "")
_HOOKS_IN_GIT_DIR="no"
_HOOKS_CONFIG_STATUS=0
git config --get core.hooksPath >/dev/null 2>&1 || _HOOKS_CONFIG_STATUS=$?
if [ -n "$_HOOK_PATH" ] && [ -n "$_HOOKS_DIR" ] && [ "$_HOOKS_CONFIG_STATUS" = "1" ] && [ ! -L "$_HOOKS_DIR" ]; then
  _HOOKS_IN_GIT_DIR="yes"
fi
GSTACK_STATE_ROOT=$(~/.claude/skills/gstack/bin/gstack-paths --get GSTACK_STATE_ROOT); : "${GSTACK_STATE_ROOT:?gstack-paths failed; reinstall with ./setup or /gstack-upgrade}"
_PREPUSH_PROMPTED=$([ -f "$GSTACK_STATE_ROOT/.redact-prepush-prompted" ] && echo "yes" || echo "no")
if [ "$_REDACT_PREPUSH" = "true" ] && [ "$_HOOKS_IN_GIT_DIR" = "yes" ] && [ "$_HOOK_STATE" != "unmanaged" ]; then
  ~/.claude/skills/gstack/bin/gstack-redact install-prepush-hook || exit $?
fi
echo "REDACT_PREPUSH: $_REDACT_PREPUSH"
echo "HOOK_STATE: $_HOOK_STATE"
echo "HOOKS_IN_GIT_DIR: $_HOOKS_IN_GIT_DIR"
echo "PREPUSH_PROMPTED: $_PREPUSH_PROMPTED"

按回显的值分派：

  1. REDACT_PREPUSH: true——这段代码安装或刷新受管理的 钩子，保留 pre-push.local 和完整的 stdin。安装器失败时， 在推送前 STOP。HOOKS_IN_GIT_DIR: no：不要安装； 请求手动集成。HOOK_STATE: unmanaged：只有当钩子是默认目录中 正常的、非符号链接的文件且没有 pre-push.local 时，才征询同意； 否则请求手动集成。悬空的符号链接属于未管理。绝不覆盖任何一方的策略。

  2. REDACT_PREPUSH 不为 true 且 PREPUSH_PROMPTED: no——一次性 提议（整机只提一次）。AskUserQuestion：

    gstack 可以安装一个按仓库生效的 git pre-push 钩子，阻止包含凭据 （API key、token、私钥）的推送。它是护栏而非强制手段—— GSTACK_REDACT_PREPUSH=skip 可以绕过它。 要为你发布所用的仓库安装它吗？

    选项：

    • A) 是——安装凭据守卫（推荐）
    • B) 否——不要再问

    如果选 A：运行 ~/.claude/skills/gstack/bin/gstack-config set redact_prepush_hook true 然后重新运行上面的代码，并应用同样的目录和未管理钩子规则。 如果选 B：运行 ~/.claude/skills/gstack/bin/gstack-config set redact_prepush_hook false。 无论选哪个答案之后都总是执行（问题失败时绝不执行；下次必须重新提议）：

    GSTACK_STATE_ROOT=$(~/.claude/skills/gstack/bin/gstack-paths --get GSTACK_STATE_ROOT); : "${GSTACK_STATE_ROOT:?gstack-paths failed; reinstall with ./setup or /gstack-upgrade}"
touch "$GSTACK_STATE_ROOT/.redact-prepush-prompted"

  3. 之前已拒绝——不作评论地继续。

**针对已就绪的既有 PR/MR 存在未决门禁发现：**当 Step 9 留下状态为 open 的门禁 发现时，在推送前查找 <branch-name> 对应的开放 PR/MR （gh pr list --head <branch-name> --state open --json number,isDraft；GitLab glab mr list --source-branch <branch-name> --output json，读取 draft）。查找 失败会在此 STOP。如果存在且不是草稿：

  1. 前导信息回显了 SESSION_KIND: spawned 或 headless：推送前 STOP。 报告未决的门禁发现（gate、路径）和该 PR/MR；不推送、不声称 已发布。之后由人来处置。
  2. 否则 AskUserQuestion 一次：A) 现在就解决这些未决项——在 Step 17 之前插入 9 → 10 → 11 → 11.5 → 12 → 13 → 14 → 14.5 → 15 → 16；B) 带 Gate edits: N open 横幅 按就绪状态发布。把 B 作为人类授权的发布记录到调用记录中；Step 19 会读取它。绝不把就绪的 PR 改成草稿。

新 PR 或已有的草稿无需提问：Step 19 会创建或保持草稿。

**幂等检查：**检查分支是否已经推送且为最新。

LOCAL=$(git rev-parse HEAD) || exit 1
REMOTE_REF=$(git ls-remote --heads origin refs/heads/<branch-name>) || {
  echo "STATUS: BLOCKED — cannot verify remote branch; restore access before pushing"
  exit 1
}
REMOTE=$(printf '%s\n' "$REMOTE_REF" | awk '{print $(1)}')
REMOTE=${REMOTE:-none}
echo "LOCAL: $LOCAL  REMOTE: $REMOTE"
[ "$LOCAL" = "$REMOTE" ] && echo "ALREADY_PUSHED" || echo "PUSH_NEEDED"

ALREADY_PUSHED：跳过推送，继续 Step 18。否则带上游跟踪推送：

git push -u origin <branch-name>

**如果推送失败，STOP。**不做 Step 19，也不声称已发布。报告错误：

  • **非快进推送：**fetch 并查看远端，然后按 Step 3 的 冲突规则合并。返回 Step 17 之前先运行 Step 5–16。绝不改写历史。
  • **认证、钩子或网络失败：**修复原因，然后即使内容未变也要重跑 Step 16， 之后再回到 Step 17。绝不绕过失败的门禁。 绝不 force-push。只有推送成功或已确认 ALREADY_PUSHED 才继续。

继续 Step 18。推送之后不再运行任何文档写入者。

Step 18：准备发布元数据

先在识别出的平台上查找 <branch-name> 对应的开放 PR/MR：

  • GitHub：gh pr list --head <branch-name> --state open --json number,title,url
  • GitLab：glab mr list --source-branch <branch-name> --output json（默认就是 open）。

空数组意味着新建；匹配到一条则提供已有的标题/身份。 查找失败或有歧义的匹配会 STOP 等待处理，绝不意味着没有 PR。 保存结果供 Step 19 复查。

pr-body 节根据该结果准备标题，然后发布； --no-pr 或自动化通道走 handoff 节。

**STOP。**在准备标题并用已验证的文档结果创建或更新 PR/MR（Step 18-19）之前，阅读 ~/.claude/skills/gstack/ship/sections/pr-body.md 并完整执行。 不要凭记忆工作——那一节才是这一步的事实来源。

**STOP。**在把分支交给协调者而不是开 PR（--no-pr 或自动化通道；Step 18）之前，阅读 ~/.claude/skills/gstack/ship/sections/handoff.md 并完整执行。 不要凭记忆工作——那一节才是这一步的事实来源。

Step 20：持久化 ship 指标

通过 gstack-review-log 为 /retro 记录指标；它自行处理项目/分支路径、 JSON 校验、存储和同步，且不接受路径参数。

~/.claude/skills/gstack/bin/gstack-review-log '{"skill":"ship","timestamp":"'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'","coverage_pct":COVERAGE_PCT,"coverage_schema":2,"coverage_pct_value":COVERAGE_PCT_VALUE,"weak_gaps":WEAK_GAPS,"tests_extended":TESTS_EXTENDED,"tests_rejected":TESTS_REJECTED,"regression_proof":REGRESSION_PROOF,"plan_items_total":PLAN_TOTAL,"plan_items_done":PLAN_DONE,"verification_result":"VERIFY_RESULT","version":"VERSION","branch":"'"$(git rev-parse --abbrev-ref HEAD)"'"}'

从更早的步骤中替换：

  • COVERAGE_PCT：Step 7 图表中的整数百分比；null/未确定记为 -1
  • COVERAGE_PCT_VALUE：Step 7 的 coverage_pct_value（门禁的 X）作为整数，缺失或被忽略时为 null
  • WEAK_GAPS、TESTS_EXTENDED、TESTS_REJECTED：Step 7 的 weak_gaps、tests_extended 和 tests_rejected 的计数（键缺失或被忽略时为 0）
  • REGRESSION_PROOF：来自 Step 7 的 {"red_at_head":N,"base_green":N,"base_unavailable":N}，缺失时为 null
  • PLAN_TOTAL：Step 8 中提取的计划项总数（没有计划文件时为 0）
  • PLAN_DONE：Step 8 中 DONE + CHANGED 项的数量（没有计划文件时为 0）
  • VERIFY_RESULT："pass"、"fail" 或 "skipped"，在 Step 9 执行完 Step 8.1 的验证清单后设置
  • VERSION：Step 12 的 NEW_VERSION；在 NO_VERSION 下为 null（不加引号）

分支由 shell 提供。无需确认即可运行。
