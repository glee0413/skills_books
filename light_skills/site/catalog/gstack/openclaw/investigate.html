系统化调试

铁律

没有先做根因调查，就不要动手修。

修症状只会变成打地鼠式的调试。每个不解决根因的修复，都让下一个 bug 更难找。找到根因，再修它。

阶段 1：根因调查

在形成任何假设之前先收集上下文。

  1. 收集症状： 读错误信息、堆栈跟踪和复现步骤。如果用户给的上下文不够，一次只问一个问题。不要一次问五个。

  2. 读代码： 从症状沿代码路径回溯到可能的原因。搜索所有引用，读失败点周围的逻辑。

  3. 检查最近的改动：

    git log --oneline -20 -- <affected-files>

    它以前能用吗？改了什么？如果是回归，根因就在那份 diff 里。

  4. 复现： 你能稳定触发这个 bug 吗？不能的话，先收集更多证据再继续。

  5. 检查记忆里同一区域以前的调试会话。同一批文件里反复出现的 bug 是架构上的坏味道。

输出："根因假设：……" …… 一个具体的、可检验的判断，说明哪里错了、为什么。

阶段 2：模式分析

看这个 bug 是否匹配某个已知模式：

竞态条件 …… 偶发，依赖时序。看共享状态的并发访问。

Nil/null 传播 …… NoMethodError、TypeError。可选值缺了防护。

状态损坏 …… 数据不一致、部分更新。检查事务、回调、钩子。

集成失败 …… 超时、非预期响应。外部 API 调用、服务边界。

配置漂移 …… 本地正常，staging/prod 失败。环境变量、特性开关、数据库状态。

缓存过期 …… 显示旧数据，清缓存就好。Redis、CDN、浏览器缓存。

还要检查：

  • 项目里的已知问题，看有没有相关条目
  • Git log 里同一区域以前的修复。同一批文件里反复出现的 bug 是架构上的坏味道，不是巧合。

外部搜索： 如果 bug 不匹配已知模式，上网搜这个错误类型。先脱敏： 去掉主机名、IP、文件路径、SQL、客户数据。搜错误类别，不要搜原始消息。

阶段 3：假设检验

在写任何修复之前，先验证你的假设。

  1. 确认假设： 在怀疑的根因处加一条临时日志、断言或调试输出。跑复现。证据对得上吗？

  2. 如果假设错了： 搜索这个错误（先脱敏敏感数据）。回到阶段 1。收集更多证据。不要猜。

  3. 三振规则： 如果 3 个假设都失败，停下。告诉用户：

    "测了 3 个假设，都不匹配。这可能是架构问题，而不是简单的 bug。"

    选项：

    • 用新假设继续调查（描述它）
    • 升级给人工审查（需要了解这个系统的人）
    • 加日志并等待（给这片区域埋点，下次抓现行）

危险信号 …… 看到任何一个，慢下来：

  • "先快速修一下" …… 没有"先"这回事。要么修对，要么升级。
  • 追数据流之前就提修复方案 …… 你在猜。
  • 每个修复都在别处暴露新问题 …… 层次错了，不是代码错了。

阶段 4：实施

根因确认之后：

  1. 修根因，不修症状。 用消除真正问题的最小改动。

  2. 最小 diff： 动的文件最少，改的行数最少。压住顺手重构邻近代码的冲动。

  3. 写一个回归测试，它要：

    • 没有修复时失败（证明测试有意义）
    • 有修复时通过（证明修复有效）

  4. 跑完整测试套件。 不允许回归。

  5. 如果修复涉及超过 5 个文件： 继续之前先向用户标明影响范围。对一个 bug 修复来说这太大了。

阶段 5：验证与报告

新鲜验证： 重新复现原始 bug 场景，确认已修好。这一步不可省略。

跑测试套件。

输出结构化的调试报告：

调试报告

  • 症状： 用户观察到了什么
  • 根因： 实际错在哪里
  • 修复： 改了什么，附文件引用
  • 证据： 测试输出、证明修复有效的复现
  • 回归测试： 新测试的位置
  • 相关： 同一区域以前的 bug、架构备注
  • 状态： DONE | DONE_WITH_CONCERNS | BLOCKED

把报告按今天的日期存到 memory/，方便以后的会话参考。

重要规则

  • 修复尝试失败 3 次以上：停下，质疑架构。 是架构错了，不是假设失败。
  • 绝不提交你无法验证的修复。 不能复现并确认，就不要发布。
  • 绝不说"这应该能修好"。 去验证、去证明。跑测试。
  • 如果修复涉及超过 5 个文件： 继续之前先告知用户。
  • 完成状态：
    • DONE …… 找到根因，应用修复，写了回归测试，所有测试通过
    • DONE_WITH_CONCERNS …… 已修复但无法完全验证（例如偶发 bug、需要 staging）
    • BLOCKED …… 调查后根因仍不明确，已升级
