七个 daemon 与一个机器人

一只 Microduck 上跑着七个常驻进程，它们共享一块板子、一条电机总线和一套 JSON-RPC 契约。把它们拆开的理由不是“微服务时髦”，而是一个很具体的故障模型：控制回路会挂，摄像头会崩，更新可能装上一版坏软件，而这只机器人可能在别人家里、没有屏幕、也没有人可以按复位键。这一章看进程边界怎么划、状态归谁、以及一版新软件怎样落到机器上又怎样被撤回。原文的完整推理见系统架构精读。

一张图：客户端、socket 与设备

 手柄        手机          笔记本上的你        远端的对端
   │ BLE/USB    │ BLE            │ ssh              │ WebRTC
   ▼            ▼                ▼                  ▼
 padd          btd            robotctl           mediad
   │            │  同一套 API 的一个子集           │
   └────────────┴────────────────┴──────────────────┘
                     │ 每个服务一个 Unix socket
                     │ JSON-RPC 2.0，一行一个对象
        ┌────────────┼─────────────┬──────────────┐
        ▼            ▼             ▼              ▼
     robotd       configd       updaterd        tofd
     50 Hz 回路   Wi-Fi/身份    验证/切换/门禁   8×8 深度
        │            │             │
        ▼            ▼             ▼
   15 舵机 + IMU   BlueZ/NM    releases/current

图的读法是“谁能回答谁”。客户端从不经过一个中心 broker，而是直接连到拥有答案的那个服务的 socket；btd、padd、mediad 只是把同一套调用从另一种传输搬进来。tofd 是个例外：它只发布深度帧，不读任何人。

只有 robotd 能碰机器人

十五个舵机和 IMU 板共享一条串行总线，50 Hz 控制回路拥有它。客户端发的是意图——“用这个速度走”“看那里”“站起来”——而不是关节角或电机电流。安全层在 robotd 内部决定什么可以执行：跌倒检测、关节与温度限制、安全姿态、deadman 心跳。任何远程或本地客户端都绕不过去。

这条规则还带来一个工程后果：robotd 的控制回路不允许阻塞在另一个服务上。它对外部世界的读取全是“最后值覆盖”的本地缓存，从不做同步 RPC。摄像头卡住只应该让感知变差，不应该给电机控制增加抖动。具体回路见 robotd 设计精读与下一章的 50 Hz 回路。

恢复路径：三个不许依赖 robotd 的服务

configd、updaterd 和 btd 在 systemd 里对 robotd 没有任何依赖，也不链接机器学习运行时和媒体栈。这不是为了对称，而是因为它们是恢复路径：一只控制回路起不来的机器人，恰恰是最需要重新配网、更新或回滚的机器人。configd 拥有 Wi-Fi 和身份而不是 robotd，理由就在这里——把配置放进控制进程，会在唯一需要它的场景里变得不可达。

mediad 和 padd 则允许依赖 robotd。没有摄像头、没有手柄的机器人，仍然是一只能被更新的机器人。mediad 还说明另一半理由：视频会话没有媒体就没有意义，PeerConnection 和媒体管线放在同一个进程里，拆开也换不来什么隔离收益。

三个恢复服务还必须满足更细的约束：所有跨服务调用都是可选的、带超时的；对端沉默或 socket 关闭是正常答案，不是异常。更新引擎给自己定的接口也是如此——它只依赖 robotd 的“健康探针”和“是否可以重启”两个抽象，最初甚至是桩实现，这既让更新系统先于控制成熟，也让它可以单独测试。

传输层不拥有状态

btd、padd、netpadd、mediad 都不拥有机器人的状态。btd 把 BLE 上的一个 API 子集转发给真正回答它的服务，只连接 robotd、configd、updaterd，不连 padd 和 tofd——一条窄带无线电扛不动原始输入流和深度帧。padd 读手柄，然后发送和 App 完全相同的意图；netpadd 是它在局域网 UDP 上的替代品；mediad 除了媒体管线，还是远程 API 的前门，把 control 数据通道上的调用代理给各服务。

手柄配对故意不放在 padd，而在 configd：绑定一个蓝牙设备需要 root 和 BlueZ，而 padd 被刻意做成一个无特权的意图客户端。让它去配置蓝牙，就等于让它拥有特权，而它每天在跑的这套 API 正是手机 App 将来要用的那套——特权一进来，这层日常验证就失效了。

tofd 是唯一拥有传感器的“非控制”服务。把它从 robotd 拆出去有很硬的理由：把一块 VL53L5/8CX 拉起来要经 I²C 上传约 90 KB 固件、耗时数秒，这条总线还和音频编解码器共用，而且大多数鸭子根本没装这个传感器。这样一段重试逻辑不属于拥有电机的进程；控制回路也不读深度，移出去不会损失任何东西。它也没有并进 mediad：深度是总线上的传感器，不是媒体管线，而且在有摄像头可标注之前它就已经有用了。

状态住在哪里

架构里有一条单写者规则：每一份状态恰好有一个拥有者，其他人只能读或订阅。落到文件系统上，分界线是“更新会不会动它”：

位置 内容 谁写
/etc/robot/robotd.toml 板子、总线端口、镜像自带的默认值 镜像或安装器；OS 更新会替换
/var/lib/robot/robotd.toml 这台机器人上有人改过的键 robotctl、策略与手柄编辑、robotd
/var/lib/robot/config/config.json 名字与配对 PIN configd，文件加 flock
/var/lib/robot/vetbook.json 终身病历：时长、里程、跌倒、换过的舵机 robotd
/opt/robot/daemon/releases/<ver>/ 二进制、策略、随包默认值 更新系统，原子替换
/opt/robot/daemon/current 指向当前发布目录的符号链接 updaterd

配置是两层：/etc 是基础层，/var/lib 只放这台机器上改过的键，robotd_params::Params::load 逐键合并，表按键合并、其他类型整体替换。这样 OS 更新可以带走镜像自己的值，而主人的修改仍然生效。用户层写坏了也不会让机器人停下：它被挪到一边，机器人用基础层继续跑，robotd 报告 degraded 并点出文件名——绝不能报 unhealthy，否则每一版发布都会因为这个任何发布都修不好的文件而被回滚。基础层坏了才是致命的，那意味着镜像坏了。

OS 更新是另一种更新，它移动了这条线。A/B 分区的板子每个槽位都有一个完整的根文件系统，/etc 跟着镜像换，只有独立分区的 /var/lib/robot 能活下来。所以“主人决定的东西”放 /var/lib，“镜像决定的东西”留 /etc。updater.toml 目前还是单层，allow_dev_keys、auto_apply 这类每台机器的决定在 A/B 更新后会被镜像值覆盖，这是一个已知的开放问题。

发布是换目录，不是打补丁

一版构建以完整目录的形式落到 /opt/robot/daemon/releases/<version>/。updaterd 验证签名、解包、移动 current 符号链接、重启相关 unit，然后问 robotd 一句 robot.health：

push 分支 ──► CI 构建并签名 ──► robotctl update apply
                                      │
                                      ▼
                    updaterd：验签、解包、移动 current、重启
                                      │
                                      ▼
                    健康门禁：robot.health
                      ├─ healthy / degraded ──► 保留
                      └─ unhealthy / 无应答 ──► 换回旧版

健康门禁把五种判定分成“提交”和“回退”两组：healthy 与 degraded 提交，unhealthy、unreachable、unreadable 回退。degraded 是板子的问题（比如舵机没供电），不是发布的问题，不能因为一块实验台上的机器人没接电源就回滚一版正确的软件。如果回滚后仍然崩溃循环，启动计数器会接手，把机器人带回黄金版本。

这个机制有两个必须记住的运维事实。第一，updaterd 不能在自己更新到一半时重启自己，所以每次更新后有大约五秒“运行中的版本”合法地落后于“已安装的版本”，任何只报一个版本号的工具在这段时间都会说谎；robotctl version 因此同时报两个并指出分歧。第二，更新引擎本身就在它要更新的那个产物里，所以开发期必须一直保留 SSH 和重新刷机这条手动路径，不能让它成为唯一的退路。

四条不变量

把这一章压缩成四句话，就是架构文档里的四条不变量：

  1. btd、configd、updaterd 必须在 robotd 死掉时仍然工作——它们是恢复路径。
  2. robotd 对安全有最终权威，客户端只能发意图。
  3. robotd 的控制回路永远不阻塞在别的服务上。
  4. 每一份状态只有一个写者。

后面几章讲的控制、感知、交互和更新，都是这四条的展开。判断一个改动是否合适，最省事的办法也是拿这四条去套：它有没有让恢复路径依赖上控制回路？有没有让某个客户端绕过安全层？有没有把同步等待放进 50 Hz 循环？有没有制造第二个写者？
