设计决策与故障史

书里很多设计像一次想清楚的，实际上是被故障推着改出来的。这一章挑六段记录，每段按“原来以为什么、实际发生了什么、留下什么规则”来写。原文见 路线图、安装路径故障、媒体 bring-up、NPU bring-up、BLE 更新、空闲 CPU 和 按需 ToF。

路线图：编号不是顺序

M1 到 M4 曾是一条有终点的队列：能走、能空中更新、更新时变不成砖。这个目标到了，0.2.0 之后的每个发布都靠 M1、M2 建的机器到达板子。之后的工作变成几条风险不同、没有先后依赖的独立轨道，所以 M5 到 M9 的编号只是标识符，“先做什么”单独有一节。

“难的是产品化，不是能力”只说对了一半：更新路径、健康门禁、恢复网和 BLE 面都建成了，也站得住；但 0.5 之后几乎全是能力，而最大的自主大脑还没移植。每个里程碑必须有一个说“完成”的测试，否则会漂。M4 是测量里程碑，它把猜测变成数字：非实时内核上回路保持 50.0 Hz，总线和 IMU 板在 /dev/ttyS2 上应答。

顺序最后定成：先 M8 策略通道；再 M5 的传输调查；M6 随发货临近按交付周期排；M7 是没有日期的调查；M9 最后。

安装路径：四连败换来一条 hook 规则

四天内四个 bug 到达板子，全在安装路径上，418 个测试和 board-test.sh 一个都没抓到。形状是同一个：on_apply 用一条命令重启多个 unit，遇到一个未知 unit 就整体失败；打包工作流漏了 unit；二进制没被 stage，btd.service 报 203/EXEC；最贵的一个是重启列表存在板子的 /etc/robot/updater.toml 里，新 daemon 永远不会被重启。更新报告成功，apply 再说 already_current，四个 Wi-Fi 修复被“验证”成无效，因为跑的二进制从来没换过。

修复收敛到两点：重启集合从发布自带的 systemd/*.service 推导，而不是读板子配置；unit 的安装放进 hooks/postinstall。由此长出通用规则：一次全新安装对板子做的每件事，都必须同样出现在 hook 里，因为 hook 是每次更新、每块板子唯一都会跑的东西。

配套的不是一个更宽的测试，而是几层互补检查：board-test.sh 解开真实产物跑 install.sh 和 postinstall；xtask 断言工作流、install.sh、hook 的清单一致；systemd-test.sh 用真 systemd 验证延迟重启确实替换了 updaterd；dev-push.sh 每次推送后读身份文件，确认 daemon 真在跑新 release。还有一个拒绝：候选版本若缺少已安装 unit 所 exec 的二进制，orphan.rs 直接拒绝并点名原因。

媒体：权限、格式与 22 fps

第一课是权限，不是编码。/dev/mpp_service 是 0600 root:root，非 root 打不开；而 mpi_enc_test 打不开时写空文件并退出 0。零退出码什么都不能证明，文件大小才是证据。这个陷阱让 Radxa 的 deb、第三方构建和自己 CI 的插件都看起来只有解码器。真相是 MPP 插件无条件注册解码器，注册编码器前先探测 MPP，探测失败就静默省略。最后装的是一条 udev 规则，把 /dev/mpp_service 和 /dev/rga 给 video 组、0660，unit 加 SupplementaryGroups=video。

第二课是 29.3 fps 来自两个互不相关的原因，单改任何一个都看不到变化。rkisp 不实现 V4L2_CID_MIN_BUFFERS_FOR_CAPTURE，算出的最小值是 2；三是一个悬崖，两块缓冲 19.7 fps，三块及以上 29.2。像素格式上，NM12 和单平面格式都映射成 NV12，v4l2src 偏好前者却跑不满；改用 UYVY 且四块以上缓冲才是 29.3，编码器在 RGA 上转换，不花 CPU。

第三课是旋转。相机装歪四分之一圈，自然的修法是在 tee 前加 videoflip。实测一次会话 5522 次 RGA 失败、丢 1565 帧、帧率 7–8、SoC 97 °C 并降频到 408 MHz：videoflip 的输出格式 RGA 不接受，MPP 退回软件转换每一帧。于是管线里什么都不转，角度通过 media.video 报告，谁显示谁转。

第四课是顺序。rkaiq_3A_server 等待 stream-start，并且会错过已经发生的那次；在推流时重启它，会永远停在等待，没有自动曝光，画面发绿。而每次更新都会在运行中的流下面重启这个引擎。修复是 drop-in 里的 ExecStartPost=-/bin/systemctl --no-block try-restart mediad.service。自动曝光还只在流开始时收敛一次；mediad::exposure 从 tee 的原始分支取平均亮度，每秒两次接管这个环，setup-rkaiq.sh 则关掉引擎的 AE，避免两个写者。

NPU：能跑、看见、代价

RK3566 的 NPU 是 0.8 TOPS、单核。第一个模型是 320×320 的 yolo11n，单类，留出集 mAP50 0.976，INT8 量化后 3.9 MB，与浮点模型对比保住 2/2 个检测。

第一道门是驱动：Armbian 在每块 Radxa Zero 3 上把 npu@fde40000 设成 disabled，原厂板有硬件、内核、驱动，却没有 NPU。脚本写 overlay，下次启动才绑定节点。

第二道门是“跑起来”和“有用”不是一回事。duck-bench 依次回答：运行时能不能加载；还看不看得见鸭子（能跑但检测不到，看起来和正常一样）；代价是多少。实测 p50 25.7 ms、p95 58.4 ms，CPU 每帧 20.7 ms，但后者包含 letterbox，而它不在延迟里；2 Hz 下都是单核的 4%。--threshold 是第一个该动的参数：量化模型的分数有自己的尺度，检测不到时先试 0.2，再怀疑转换。

规则是：先把“能运行”“能检测”“代价”拆成三个可独立失败的测量，再谈接进行为。librknnrt.so 用 dlopen 而不是链接，也是同一类决定：厂商 blob 不在 Debian 里，链接它会让 cargo board --bins 在笔记本上失败。

BLE 更新：一次“什么都没发生”

这一类路径大部分早就存在：btd 路由了更新子集，updaterd 会推流，duck-btctl 能调全部方法。没人真的驱动过。一驱动就发现，update.subscribe 之后再 update.apply，apply 会被写进一个 stream_progress 已不再读的 socket：不运行、不回复、不报错。原因是每个服务每个会话只有一个连接，而守护进程一次只服务一个请求。修法不是每次调用一个连接，而是按连接会被占用多久分组：Prompt、Slow、Operation、Stream 各走自己的连接，lane 和权限、目标服务一起写在 route.rs 里。

第二个问题是进度成了瞄准 20 字节管道的消防水管：每个 HTTP chunk 都上报，客户端落后就丢行，百分比会从 12 跳到 61 再回到 34。现在引擎里合并成每整百分点最多一条、每秒最多四条。第三，update.check 在更新期间阻塞在引擎锁上，现在立刻回 BUSY。第四，回滚与选择开放给手机：apply 本来就能装从未跑过的代码，而 rollback/select 只切到昨天跑过的版本；该拒绝的是 pin——误触一次就把机器人钉住，之后拒绝所有更新还报告自己最新。

客户端还要接受：apply 回复后约五秒，btd 重启，连接断开。顺序是“回复即结果 → 断开 → 重连读 update.status”。超时也从总预算改成静默预算，一次更新三分钟，因为那是两次合法进度之间最长的间隔。

空闲 CPU：先量线程，再设计开关

一台没人用的鸭子仍跑五个守护进程。mediad 每秒复制 30 次 1.84 MB，而读它的两个消费者合计每秒两次；测试图案按相机分辨率用 CPU 画，720p30 占单核 29.4%，相机路径只要 6.1%；tofd 每秒做约 100 次 I²C 读；padd 每秒重发 50–100 条相同的零；pet-detect 每秒做 400 次 FFT。

修法都很小：帧只在读者要时拷贝，而且回答下一帧，避免曝光环振荡；测试图案降到 256×144@5；ToF 轮询跳过传感器还不可能出帧的那段；padd 只抑制“不要求运动”的相同帧；宠物分类器等到房间有异常声音再跑。

也有故意不改的。safety.apply 每 tick 写十六个目标，包括停着不动的 tick；算下来不到单核的 0.1%。改成条件写就要枚举所有会让伺服目标失效的路径——力矩开关、掉电、伺服重启、init 插值——错一个就是机器人不再保持姿势。多线程 tokio 运行时同理：空闲 worker 会 park，不轮询，省下的是内存不是热。

转折来自 ps -L：tofd 空闲的约 5% 里，4.5% 是头部 IMU，0.5% 是深度；而 head_imu.stream 没有任何消费者。于是按需启停 unit 被放弃，改成 [head_imu] enabled 默认关闭。按需测距只省 0.5%，却要在共享 I²C 总线里加状态机、恢复路径和未验证的硬件假设；启停 unit 更糟：每次要传 90 KB 固件、花几秒，而且没人负责关。

规则是：先按线程测量，再决定优化哪一层；以及一个没有消费者的传感器，最该关掉的是传感器，而不是把它优化得更便宜。

五条留下来的规则

  • 测试贴着真实产物：解开 tarball、跑 install.sh、用真 systemd。
  • 清单互相证明：打包、安装、hook、重启集合，手写列表都要有测试对齐。
  • 在离源头最近处测量：捕获率在 tee 前的 pad，CPU 按线程，权限先于插件。
  • 报告，不替消费者决定：旋转角度、量化分数、时间戳。
  • 先量再设计：按需启停、条件写总线、换运行时，常常只省下噪声。
