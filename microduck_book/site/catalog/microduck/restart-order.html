重启顺序

更新不是“换完文件就结束”。updaterd 要决定哪些 unit 在什么时候重启、哪些必须等回复发完再重启，以及开机后如何确认它们真的从新 release 起来了。

更新时

update.apply 的顺序大致是：验证、解包、移动 current、重启 release 带来的 units、跑 postinstall hook、自测新的 updaterd、健康门禁、提交。重启集合来自 release 自己的 systemd/*.service，不是板子上的配置。

updaterd 和 btd 不能在同一时刻被重启：前者正在执行更新，后者可能正在把回复送回手机。它们通过 systemd-run --on-active=5s 延迟重启，等 update.apply 的结果先写到 wire 上。这个 5 秒不是随便的等待，而是“回复已经发出”的边界。

开机时

每个 unit 按 systemd 依赖启动，但更新系统还要做一次对账：updaterd 在启动时读取 current、release 的 unit 列表和运行状态，确认新 release 的 daemon 确实起来了。如果没起来，boot counter 或 boot recovery net 会介入。

诊断版本漂移

robotctl health 的 unit 块会打印每个进程正在从哪个 release 运行，这是确认“延迟重启到底有没有发生”的唯一地方。一个进程还在旧目录、或者某个 unit 没重启成功，都会在这里暴露。不要只看 current 指向哪里。

设计教训

把重启列表放在 /etc/robot/updater.toml 曾是 bug：install.sh 会保留这个文件，于是新加的 daemon 永远不会被重启。现在列表从 release 的 unit 文件推导，NEVER_RESTART 写在代码里，因为“哪些 daemon 是更新执行者”是结构属性，不是 operator 该配置的选项。
